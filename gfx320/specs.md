# GFX320.DLL — техническое задание

## 1. Назначение

`GFX320.DLL` — графическая библиотека для компьютера Sprinter, предназначенная для
быстрого вывода 2D-графики в режиме 320×256×256 цветов.

Библиотека должна предоставлять:

- аппаратно ускоренные заливки и копирование прямоугольных областей;
- горизонтальные и вертикальные линии;
- работу с двумя экранными буферами;
- управление аппаратным DRAM-зеркалом видеопамяти;
- аппаратную прозрачность по индексу `#FF`;
- быстрый вывод тайлов 16×16;
- пакетный вывод последовательностей тайлов, tilemap и metatile;
- быструю загрузку 256-цветной палитры;
- пошаговые fade-in/fade-out, синхронизируемые кадровым ISR приложения;
- проверяемые функции без неявного clipping, отдельные быстрые функции с
  заранее проверенными параметрами и явно названные медленные `_clip` entry.

Библиотека должна использовать ABI libman 1.2/1.3 и собираться в формате L0.
Рабочее имя файла — `GFX320.DLL`.

Для тайлового вывода библиотека использует два разных CPU-окна:

- WIN0 — фиксированное source window с физической страницей тайлов;
- VRAM window — назначение в видеопамяти.

VRAM window не может перекрывать окно с кодом DLL или текущим стеком. На всё
время, пока страница тайлов подключена в WIN0, maskable interrupts запрещены,
а `RST`/BIOS/DSS-вызовы не выполняются. Дополнительный контракт для NMI и
WIN0 определён в §15.

## 2. Границы первой версии

Поддерживается только графический режим DSS `#81`:

- разрешение: 320×256;
- глубина: 8 бит на пиксель;
- размер строки: 320 байт;
- размер одного экранного буфера: 81 920 байт;
- два экранных буфера;
- индекс прозрачного цвета: `#FF`.

Обязательный MVP состоит только из этапов 0–3:

- инициализация и безопасное управление окнами;
- `gfx_clear_buffer`;
- `gfx_fill_rect`;
- `gfx_hline` и `gfx_vline`;
- `gfx_set_page_table`, `gfx_draw_tile`, `gfx_draw_tile_fast`;
- `gfx_draw_tile_span` и `gfx_draw_tile_list`;
- минимальные ASM/EXE-тесты этих функций.

Палитровые функции этапа 4 являются optional MVP и не блокируют выпуск:
приложение может настроить палитру самостоятельно. Копирование экранных
областей, swap, clipping тайлов, tilemap/metatile, fade и все дополнительные
примитивы относятся к post-MVP.

Не входят в первую версию:

- режим 640×256×16;
- ZX-видеорежимы;
- неподдерживаемый текущим DSS режим `#80`;
- масштабирование и поворот изображений;
- альфа-смешивание;
- чтение итоговой VRAM-картинки, содержащей объекты, записанные с
  `VRAM_ONLY`;
- runtime-конвертация графических ассетов между разными layout;
- аппаратные OR/XOR/AND-композиции до отдельной проверки точного протокола
  `FN_ACC` на реальном компьютере.

## 3. Аппаратная модель

### 3.1 Экранные буферы

При подключённой VRAM-странице в выбранном CPU-окне:

- buffer 0 начинается по адресу `WINDOW_BASE + #000`;
- buffer 1 начинается по адресу `WINDOW_BASE + #140`;
- `PORT_Y=#89` выбирает строку `0..255`;
- X задаётся смещением `0..319` от базы буфера.

Физическая строка VRAM имеет размер 1024 байта. Внутри строки:

```text
#000..#13F  пиксели buffer 0
#140..#27F  пиксели buffer 1
#300..#39F  дескрипторы 40 экранных ячеек
#3E0..#3FF  палитровые регистры и связанные поля
```

Запись за правую границу пиксельного буфера не является безобидным
«рисованием за экраном»: она может изменить соседний буфер, дескрипторы
видеорежима или палитру.

Если VRAM подключена в WIN3, стандартные базы имеют вид:

```text
buffer 0: #C000 + X
buffer 1: #C140 + X
```

Вся арифметика X должна быть 16-битной. Использование только младшего байта
недопустимо, поскольку координаты `256..319` иначе заворачиваются в левую часть
экрана.

### 3.2 Режимы записи VRAM

Младшие флаги номера VRAM-страницы определяют поведение записи:

| Страница | Прозрачность `#FF` | Обновление DRAM-зеркала | Назначение |
|---|---:|---:|---|
| `#50` | нет | да | обычный фон |
| `#54` | нет | нет | непрозрачный временный объект |
| `#58` | да | да | прозрачная фоновая графика |
| `#5C` | да | нет | прозрачный спрайт |

Физическая видеоплоскость для этих алиасов одна и та же. Меняется только
поведение записи.

Чтение через стандартное окно VRAM возвращает данные DRAM-зеркала. Поэтому
`copy_rect` и `copy_buffer` копируют сохранённый фон. Объекты, ранее выведенные
с `VRAM_ONLY`, в источнике отсутствуют.

### 3.3 Два экрана

Порт `RGMOD=#C9`, бит 0, выбирает отображаемый буфер:

```text
front = RGMOD & 1
back  = front ^ 1
```

При использовании назначения `FRONT` или `BACK` библиотека должна прочитать
`RGMOD` один раз в начале публичной операции. Пакетная операция не должна
повторно читать `RGMOD` для каждого тайла.

### 3.4 Акселератор

Используемые команды:

| Команда | Инструкция | Назначение |
|---|---|---|
| IDLE | `LD B,B` | выбрать неактивный `ACC_MODE=0` |
| FILL | `LD C,C` | горизонтальная заливка |
| SET_BUFFER | `LD D,D` | установить длину блока |
| FILL_VERT | `LD E,E` | вертикальная заливка |
| COPY | `LD L,L` | горизонтальное копирование |
| COPY_VERT | `LD A,A` | вертикальная фаза копирования с инкрементом `PORT_Y` |

У вертикальных команд адрес CPU не получает ни шаг 320, ни шаг 1024. Во время
каждого элемента адрес остаётся постоянным, а аппаратно увеличивается
`PORT_Y`. Следствия:

- `FILL_VERT` корректно заполняет одну X-колонку, потому что фазы чтения
  источника у заливки нет;
- прямой `COPY_VERT` из обычной DRAM-страницы не собирает колонку: он повторно
  читает один и тот же адрес;
- в прямом VRAM→VRAM копировании один `PORT_Y` используется обеими фазами,
  поэтому этим путём нельзя независимо задать Y источника и назначения;
- вертикальная выгрузка заранее подготовленного непрерывного блока возможна:
  обычный `COPY` сначала загружает блок во внутренний буфер акселератора,
  `IDLE` завершает фазу, после чего `COPY_VERT` записывает этот блок в
  постоянный X при изменяющемся `PORT_Y`. Этот двухфазный приём используется
  работающим `AFNT320`, но он не является прямым DRAM→VRAM `COPY_VERT`.

Требования:

- аппаратная операция выполняется при запрещённых прерываниях;
- каждая блочная процедура завершается `LD B,B` непосредственно после своей
  последней trigger-инструкции; переносить `IDLE` за подготовку следующей
  строки или объединять несколько блоков без терминатора запрещено;
- перед возвратом `PORT_Y` устанавливается в `#C0`;
- нулевое аппаратное значение длины означает 256 байт;
- на уровне публичного API `width=0` или `height=0` всегда означает пустую
  операцию, а не 256 пикселей;
- операции длиннее 256 байт разбиваются на несколько блоков;
- библиотека должна сохранять и восстанавливать изменяемое CPU-окно.

`LD B,B` не выключает акселератор через порт и не меняет глобальный режим
компьютера: это обычный M1-опкод, выбирающий `ACC_MODE=0`. GFX320 не должна
трогать глобальный enable акселератора или `ALL_MODE/#C3`.

Последовательность имеет строгую форму:

```text
выбор команды → параметры/trigger → LD B,B
```

Это относится также к `SET_BUFFER`: после `LD D,D` и принятия байта размера
сразу выполняется `LD B,B`. Следующая строка или колонка начинает новую
блочную процедуру с нового выбора команды.

Вся последовательность от выбора команды/`SET_BUFFER` до непосредственного
`IDLE` атомарна относительно прерываний. Прерывание между `LD D,D` и
завершением операции разрушает состояние акселератора; `RETI` также содержит
M1-циклы, которые нельзя допускать внутри незавершённой команды.

`FN_ACC` не включается в ABI 1.0. Регистр функции перезащёлкивается M1-фетчем
ALU-опкодов диапазона `#80..#BF`: случайный `OR A`, `XOR A` или иной такой
опкод между селектором и запуском молча меняет операцию. Пример селектора
`LD D,(HL)` из старого manual не считается достаточной спецификацией.

### 3.5 Палитра

Палитры двух экранов находятся в той же VRAM-странице `#50`:

```text
buffer 0 palette: #x3E0 = R, #x3E1 = G, #x3E2 = B
buffer 1 palette: #x3E4 = R, #x3E5 = G, #x3E6 = B
PORT_Y           = palette index 0..255
```

В записи `#x3E0` символ `x` означает старшие биты выбранного 16-КБ CPU-окна.
Для регистров внутри строки декодируются младшие 10 бит адреса, поэтому
смещения `#03E0/#43E0/#83E0/#C3E0` эквивалентны при подключении VRAM в
соответствующее окно. Палитровые поля buffer 1 имеют смещение `+4`.

Компоненты RGB имеют полную 8-битную точность. Быстрый путь не должен вызывать
BIOS `PIC_SET_PAL` для каждого цвета. Палитра загружается прямой записью в
регистры через VRAM-окно.

## 4. Общие требования к ABI

### 4.1 Типы

```text
u8      беззнаковое 8-битное значение
u16     беззнаковое 16-битное значение, little-endian
i8      знаковое 8-битное смещение
s16     знаковое 16-битное смещение, little-endian; не координата
TileRef двухбайтовая ссылка на тайл
```

Экранные координаты всегда беззнаковые: `x` имеет тип `u16` и диапазон
`0..319`, `y` — `u8` и диапазон `0..255`. Отрицательные координаты не входят в
ABI 1.0.

API имеет три семантических яруса, но не обязан предоставлять все три варианта
для каждой операции:

- обычный `gfx_*` проверяет аргументы; любой выход области за экран возвращает
  `GFX_ERR_ARGUMENT`, не изменяя экран;
- `gfx_*_fast` не проверяет координаты и размеры; нарушение предусловий — UB;
- `gfx_*_clip` явно обрезает область и потому заведомо медленнее.

В ABI 1.0 отдельный clip-entry требуется только для одиночного тайла:
`gfx_draw_tile_clip`. Остальные clip-варианты добавляются только по
подтверждённой необходимости и только в конец таблицы entry.

### 4.2 Возврат ошибок

Контракт библиотеки проверяется по `A`:

```text
A = 0             успех
A = GFX_ERR_*     ошибка самой GFX320
```

`CF` не используется как канал ошибок GFX320. `libman l_call` версий 1.2/1.3
не передаёт carry обычного DLL-entry вызывающему: после возврата он формирует
`CF` из собственного состояния. Поэтому вызывающий использует два уровня
проверки:

```text
CALL LIBMAN.l_call
JR C, libman_error       ; handle/mapping/dispatch, детали у libman
OR A
JR NZ, gfx_error         ; A = GFX_ERR_*
```

Для entry 0 (`gfx_init`) libman дополнительно трактует carry DLL как
init-failure: `gfx_init` возвращает `CF=1` при `A!=0` и `CF=0` при `A=0`.
Для entry `>=1` состояние `CF` не является частью публичного ABI: принудительно
формировать его на каждом горячем возврате не требуется.

Предлагаемые коды:

| Код | Имя | Значение |
|---:|---|---|
| `#10` | `GFX_ERR_ARGUMENT` | некорректный параметр |
| `#11` | `GFX_ERR_VIDEO_MODE` | активен не режим `#81` |
| `#12` | `GFX_ERR_WINDOW` | конфликт CPU-окна с библиотекой |
| `#13` | `GFX_ERR_PAGE` | логическая страница отсутствует |
| `#14` | `GFX_ERR_TILE` | слот тайла больше 63 |
| `#15` | `GFX_ERR_PALETTE` | базовая палитра не загружена |
| `#16` | `GFX_ERR_BUSY` | конфликт внутренней операции |
| `#17` | `GFX_ERR_UNSUPPORTED` | комбинация флагов не поддерживается |

Диапазон `#01..#0F` оставлен менеджерам/обёрткам. Это позволяет C-binding
возвращать единый однобайтовый статус без коллизии с известными ошибками
libman. Обновлённый Turbo Pascal `LIBMAN.INC` уже хранит `LibErr` отдельно и
не требует такого разнесения, но единый диапазон сохраняется для остальных
binding и диагностических журналов.

Быстрые функции с суффиксом `_fast` могут не выполнять полную проверку
аргументов, но обязаны документировать предусловия.

### 4.3 Ограничения `libman l_call`

Перед вызовом диспетчера приложение устанавливает:

```text
HL = handle DLL
B  = номер entry
C  = зарезервирован libman
```

До entry библиотеки гарантированно доходят только `A`, `DE`, `IX`, `IY`.
`HL` и `BC` используются `l_call` и не могут нести параметры; возвращаемое
`HL` также будет заменено восстановленным handle. Входные флаги не
сохраняются: диспетчер выполняет арифметику при вычислении адреса entry.
Альтернативный набор не считается гарантированным, поскольку путь включает
`RST #10 SETWIN`, а его сохранность для всех DSS не является контрактом.
Поэтому:

- простые вызовы используют `A`, `DE`, `IX`, `IY`;
- параметры компактных и горячих функций при необходимости упаковываются в
  свободные биты `DE/IX`;
- только функции, чей полный набор координат/размеров/флагов не помещается в
  `A`, `DE`, `IX`, `IY`, получают в `DE` указатель на packed descriptor;
- альтернативный набор не является частью публичного ABI 1.0;
- небольшие descriptor полностью копируются во внутренний scratch до
  подключения source/VRAM-окон;
- публичные функции сохраняют все регистры, не объявленные входом или
  результатом конкретного entry.

Полезный результат не возвращается в `A`, чтобы не конфликтовать с ошибкой:
`gfx_fade_step` возвращает признак в `E`, `gfx_get_pixel` — цвет в `E`,
`gfx_get_version` — версию в `DE` и capabilities в `IX`.

Вход `A` для `gfx_init` не определён и не является файловым handle или
указателем на payload. При ошибке самого `l_call` (`CF=1`) значение `A` также
не является диагностическим кодом; приложение использует канал ошибок своего
менеджера. В native libman handle передаётся как `HL` с обязательным `H=0`.
Перед `l_info` вызывающий обязан выполнить `OR A`: ошибочная реализация через
`RLA` учитывает входной `CF`; `l_info` временно использует WIN3.

`l_call` нереентерабелен из-за статического состояния и модифицируемого кода
восстановления окна. Любые вызовы libman из ISR запрещены. Выполняемые внутри
`corecall` entry `gfx_init`/`gfx_free` сами не вызывают `l_call`/`l_free`.

Для C поставляются wrapper-функции. SDK использует SDCC 2.9.0 без
`__sdcccall`: аргументы лежат на стеке, `IX` является сохраняемым frame
pointer, а существующие assembler-wrapper также используют `IY` для чтения
аргументов. Обёртка копирует аргументы в статический scratch, сохраняет `IX`,
загружает `IX/IY` ABI библиотеки последними и не ожидает, что `l_call` их
сохранит. Напрямую объявлять регистровый ABI обычной C-функцией нельзя.

### 4.4 Реентерабельность

Первая версия не обязана быть реентерабельной. Запрещено вызывать функции
GFX320 повторно из обработчика прерывания во время другой операции GFX320.

Неблокирующий fade не удерживает акселератор между вызовами.

### 4.6 Регистровый ABI entry

| Функция | Вход при вызове `l_call` | Результат при `A=0` |
|---|---|---|
| `gfx_init`, `gfx_free` | нет | `A=0` |
| `gfx_set_vram_window` | `E=window 1..3` | `A=0` |
| `gfx_get_version` | нет | `D=ABI major`, `E=ABI minor`, `IX=capabilities` |
| `gfx_get_config` | `DE=&GfxConfig` | заполненная структура, `A=0` |
| `gfx_clear_buffer` | `A=color`, `E=flags` | `A=0` |
| `gfx_fill_rect` | `DE=&GfxFillRect` | `A=0` |
| `gfx_hline`, `gfx_vline` | `IX=x`, `IYH=0`, `IYL=y`, `DE=length_flags`, `A=color` | `A=0` |
| `gfx_copy_rect` | `DE=&GfxCopyRect` | `A=0` |
| `gfx_copy_buffer` | `D=source`, `E=destination_flags` | `A=0` |
| `gfx_restore_background_rect` | `DE=&GfxRestoreRect` | `A=0` |
| `gfx_palette_load256` | `DE=source`, `A=palette_mask` | `A=0` |
| `gfx_palette_load_range` | `DE=source`, `IX=count_mask`, `A=first` | `A=0` |
| `gfx_palette_set` | `A=index`, `D=r`, `E=g`, `IXH=mask`, `IXL=b` | `A=0` |
| `gfx_fade_begin` | `A=direction`, `D=duration`, `E=palette_mask` | `A=0` |
| `gfx_fade_step` | нет | `A=0`, `E=0` finished или `E=1` active |
| `gfx_fade_cancel` | нет | `A=0` |
| `gfx_swap_buffers` | нет | `A=0` |
| `gfx_set_page_table` | `DE=source`, `IX=page_count` | `A=0` |
| `gfx_draw_tile`, `gfx_draw_tile_fast`, `gfx_draw_tile_clip` | `DE=TileRef`, `IX=x`, `IYH=0`, `IYL=y`, `A=flags` | `A=0` |
| `gfx_draw_tile_span` | `DE=&GfxTileSpan` | `A=0` |
| `gfx_draw_tilemap` | `DE=&GfxTilemap` | `A=0` |
| `gfx_draw_metatile` | `DE=&GfxMetatile` | `A=0` |
| `gfx_draw_tile_list` | `DE=&GfxTileList` | `A=0` |
| `gfx_draw_rect` | `DE=&GfxDrawRect` | `A=0` |

| `gfx_get_pixel` | `IX=x`, `IYH=0`, `IYL=y`, `E=source` | `A=0`, `E=color` |
| `gfx_line` | `DE=&GfxLine` | `A=0` |
| `gfx_move_rect` | `DE=&GfxMoveRect` | `A=0` |
| `gfx_scroll_rect` | `DE=&GfxScrollRect` | `A=0` |

Через память передаются только:

- `GfxFillRect`/`GfxDrawRect`;
- `GfxCopyRect`/`GfxRestoreRect`/`GfxMoveRect`/`GfxScrollRect`;
- `GfxTileSpan`/`GfxTilemap`/`GfxMetatile`/`GfxTileList`;
- `GfxLine`;
- выходная структура `GfxConfig`.

Это не внутренний универсальный calling convention: все остальные параметры
передаются регистрами. Descriptor копируется один раз на входе; пакетные
операции не перечитывают его для каждой строки или каждого тайла.

Все структуры packed, little-endian; после соответствующей точки фиксации из
§18 их размер в ABI 1.0 не меняется. Поля `reserved` вызывающий обнуляет.
Конкретные поля структур определены в разделах соответствующих функций.

`GfxConfig`:

```text
offset size field
0      1    struct_size
1      1    required_dss_mode = #81
2      2    width = 320
4      2    height = 256
6      1    vram_window
7      1    source_window
8      1    code_window
9      1    mapping_flags
10     2    capabilities
12     1    tile_width = 16
13     1    tile_height = 16
14     1    tile_layout (`GFX_TILE_ROW_MAJOR`)
15     1    reserved = 0
```

Для ABI 1.0 `D=1`, `E=0`. Поле/регистр `capabilities`:

```text
bit 0  GFX_CAP_ACCELERATOR
bit 1  GFX_CAP_DRAM_MIRROR
bit 2  GFX_CAP_KEY_FF
bit 3  GFX_CAP_DOUBLE_BUFFER
bit 4  GFX_CAP_PALETTE_RGB8
bit 5  GFX_CAP_FADE
bit 6  GFX_CAP_TILES
bit 7  GFX_CAP_WIN0_TILE_SOURCE
bits 8..15 reserved = 0
```

Capabilities отражают реально реализованные entry данной сборки, а не только
теоретические возможности компьютера.

Перед вызовом `gfx_get_config` вызывающий записывает в `struct_size` ёмкость
своей структуры. DLL запоминает её, заполняет не более
`min(input_struct_size, 16)` байт и возвращает в байте 0 полный известный ей
размер `16`. Значение `0` возвращает `GFX_ERR_ARGUMENT`. Это позволяет
расширять хвост структуры без чтения/записи за буфер старого клиента.

Для ABI 1.0 `source_window=0`, а `mapping_flags` содержит
`GFX_MAPPING_SOURCE_WIN0` в bit 0; bits `1..7` равны нулю. После успешного
`gfx_init` VRAM window обязано быть настроено и находиться в WIN1..WIN3.

## 5. Флаги назначения и записи

Флаги передаются каждой рисующей или пакетной операции. Глобального
`gfx_set_write_mode` в основном API нет.

```text
bits 0..1 — назначение
  00 GFX_DST_BUFFER0
  01 GFX_DST_BUFFER1
  10 GFX_DST_FRONT
  11 GFX_DST_BACK

bit 2 — GFX_WRITE_VRAM_ONLY
  0: запись в VRAM и DRAM-зеркало
  1: запись только в VRAM

bit 3 — GFX_WRITE_KEY_FF
  0: непрозрачная запись
  1: байт #FF не записывается

bits 4..7 — зарезервированы и должны быть равны 0
```

VRAM-алиас вычисляется как:

```text
vram_page = #50 | (flags & #0C)
```

`GFX_WRITE_KEY_FF` допустим для тайлов и копирования данных. Для сплошной
заливки, очистки и линий этот флаг считается ошибкой `GFX_ERR_UNSUPPORTED`.
Clipping не кодируется во флагах: он определяется именем отдельного entry.

## 6. Управление библиотекой

### 6.1 `gfx_init`

Обязанности:

- определить окно, в котором размещена DLL, по старшему байту адреса кода;
- зафиксировать `source_window=WIN0`;
- выбрать VRAM window среди WIN1..WIN3, не совпадающее с окном DLL и текущего
  `SP`;
- при первой инициализации сбросить внутреннее состояние;
- установить `PORT_Y=#C0`;
- пометить палитру и таблицу страниц как неинициализированные.

Инициализация не должна автоматически очищать экран или изменять палитру.

Определение номера собственного окна выполняется только после маскирования:

```z80
LD A,H
AND #C0
RLCA
RLCA          ; A = 0..3
```

Вариант `RRCA`×6 без предварительного `AND #C0` запрещён: младшие биты адреса
кода попадают в результат.

Повторный `gfx_init` идемпотентен: он повторно проверяет окна, но не
очищает экраны, не меняет палитру и не сбрасывает установленную приложением
page table. Активный fade при повторной инициализации отменяется с сохранением
текущей аппаратной палитры.

Entry 0 вызывается самим `l_load`, пока загрузчик ещё держит своё внутреннее
состояние отображения страниц. Поэтому `gfx_init` не вызывает DSS/BIOS и не
опрашивает `GETVMOD`: это обязанность приложения. До первого рисующего вызова
приложение обязано включить DSS-режим `#81` и не менять его до `gfx_free`.
`GfxConfig.required_dss_mode` сообщает требуемое значение. Debug-сборка может
проверять режим на границе прикладной обёртки, но не из loader hook.

### 6.2 `gfx_free`

Обязанности:

- установить `PORT_Y=#C0`;
- восстановить временно удерживаемые аппаратные состояния;
- не менять текущий видеорежим.

По инварианту публичных функций при входе в `gfx_free` незавершённой команды
акселератора быть не может. `gfx_init` и `gfx_free` не пишут в порт глобального
управления акселератором и не выполняют `LD B,B` без предшествующей команды
самой GFX320.

### 6.3 `gfx_set_vram_window`

Позволяет выбрать WIN1..WIN3 для подключения VRAM.

Регистры:

```text
E = vram_window
```

Требования:

- запрещать WIN0, поскольку он зарезервирован под source page тайлов;
- запрещать окно, содержащее код DLL;
- запрещать окно, в котором находится текущий `SP`;
- сохранять вычисленную CPU-базу и порт страницы;
- возвращать ошибку для значения вне `1..3`;
- не менять конфигурацию при ошибке.

Проверка `SP` защищает только момент конфигурации. Перед каждой публичной
операцией библиотека повторно проверяет текущий `SP`; конфликт с VRAM window
даёт `GFX_ERR_WINDOW` до первого изменения mapping.

### 6.4 Фиксированное source window

Тайловый source window в ABI 1.0 всегда WIN0 (`#0000..#3FFF`, page port
`#82`). Публичного setter для него нет; entry 3 зарезервирован.

Перед подключением страницы тайлов библиотека:

1. заранее читает все параметры и ссылки текущего тайла в регистры/scratch;
2. сохраняет исходную страницу WIN0 и состояние interrupts;
3. выполняет `DI`;
4. прямой записью в `#82` подключает физическую страницу тайлов;
5. выводит один тайл;
6. восстанавливает WIN0 и только затем исходное состояние interrupts.

Между шагами 3–6 запрещены `RST`, BIOS/DSS-вызовы и чтение данных приложения
из WIN0. Обычный стек не переносится и продолжает находиться вне VRAM window.

Текущий MVP использует обычные `CALL`/`RET` внутри tile-loop, поэтому для
тайловых entry действует дополнительное ограничение размещения: сама DLL и
текущий `SP` должны находиться в WIN1..WIN3. DLL, загруженная в WIN0, может
использовать только примитивы без source page; `gfx_draw_tile`, `_fast`,
`_span` и `_list` возвращают `GFX_ERR_WINDOW` до подключения страницы тайлов.
То же относится к вызову тайлового entry при стеке в WIN0. Это ограничение
исчезнет только при отдельном безстековом tile-core; ABI 1.0 на него не
рассчитывает.

### 6.5 Кадровая синхронизация

Кадровая синхронизация находится вне GFX320:

- библиотека не предоставляет `gfx_vsync`;
- библиотека не опрашивает `#FFFE` и не ожидает короткое окно blank;
- библиотека не устанавливает, не патчит и не подменяет ISR;
- библиотека не управляет CBL ради получения кадрового события.

Приложение или его runtime обслуживает кадровый IRQ и устанавливает собственный
frame flag/counter. Основной код приложения, увидев событие, вызывает
`gfx_swap_buffers` и/или `gfx_fade_step`. Вызывать GFX320 непосредственно из ISR
запрещено правилами нереентерабельности и управления окнами.

### 6.6 `gfx_swap_buffers`

Переключает бит 0 `RGMOD`. Не выполняет автоматическую полную копию экранов.
Функция выполняется немедленно и не ожидает кадрового события; правильный
момент вызова определяет приложение по своему ISR.

Отдельный вызов `gfx_copy_buffer` применяется, когда приложению нужна
синхронизация содержимого.

## 7. Графические примитивы

### 7.1 `gfx_clear_buffer`

```text
gfx_clear_buffer(color, flags)
```

Заливает выбранный буфер целиком цветом `color`.

Требования к реализации:

- использовать 320 вертикальных `FILL_VERT`;
- высота каждой операции равна 256;
- очищать только выбранный buffer 0/1/front/back;
- поддерживать запись с обновлением зеркала и `VRAM_ONLY`;
- не принимать `KEY_FF`;
- биты флагов `4..7` должны быть нулевыми.

### 7.2 `gfx_fill_rect`

```text
gfx_fill_rect(x, y, width, height, color, flags)
```

`GfxFillRect`:

```text
offset size field
0      2    x
2      1    y
3      2    width
5      2    height
7      1    color
8      1    flags
9      3    reserved = 0
```

Заливает прямоугольник:

```text
[x, x + width) × [y, y + height)
```

Требования:

- `width=0` или `height=0` — успешная пустая операция;
- `x>319`, `x+width>320` или `y+height>256` возвращает
  `GFX_ERR_ARGUMENT` без записи;
- выбирать вертикальную или горизонтальную заливку по числу команд и
  стоимости переключений `PORT_Y`;
- полный прямоугольник 320×256 перенаправлять в `gfx_clear_buffer`;
- не принимать `KEY_FF`.

Рекомендуемая эвристика:

- вертикальный путь, если число байтовых колонок не больше числа строк;
- горизонтальный путь в остальных случаях;
- реальный выбор уточнить по benchmark на железе.

### 7.3 `gfx_hline`

```text
gfx_hline(x, y, length, color, flags)
```

Рисует горизонтальную линию толщиной один пиксель.

Регистровый ABI:

```text
IX = x
IYH = 0
IYL = y
A  = color
DE = length_flags

length = DE & #01FF
flags  = (DE >> 9) & #0F
bits 13..15 = 0
```

Длина `0..320` занимает 9 бит; четыре destination/write flags помещаются в
оставшиеся биты без обращения к памяти.

Требования:

- `length=0` — успешная пустая операция;
- использовать горизонтальный `FILL`;
- длины больше 256 разбивать на блоки;
- при `x+length>320` возвращать `GFX_ERR_ARGUMENT`;
- не принимать `KEY_FF`.

### 7.4 `gfx_vline`

```text
gfx_vline(x, y, length, color, flags)
```

Рисует вертикальную линию толщиной один пиксель.

Использует тот же регистровый ABI и упаковку `length_flags`, что `gfx_hline`.
Допустимая длина `0..256`.

Требования:

- `length=0` — успешная пустая операция;
- использовать один `FILL_VERT`, если длина `1..256`;
- при `y+length>256` возвращать `GFX_ERR_ARGUMENT`;
- не принимать `KEY_FF`.

### 7.5 `gfx_draw_rect`

```text
gfx_draw_rect(x, y, width, height, color, flags)
```

Рисует только рамку прямоугольника, не изменяя внутреннюю область.
`GfxDrawRect` совпадает по layout с `GfxFillRect`.

Семантика малых размеров:

- `width=0` или `height=0` — пустая операция;
- `height=1` — одна горизонтальная линия;
- `width=1` — одна вертикальная линия;
- остальные случаи — две горизонтальные и две вертикальные линии без
  повторной записи углов, если это повышает скорость.

### 7.6 `gfx_put_pixel` и `gfx_get_pixel`

Вспомогательные, не предназначенные для горячих циклов.

`gfx_put_pixel` пишет цвет с учётом назначения и режима зеркала.
При `GFX_WRITE_KEY_FF` и `color=#FF` вызов успешно не выполняет запись.

`gfx_get_pixel` читает пиксель из DRAM-зеркала выбранного буфера. Документация
обязана явно указывать, что функция не видит изменения `VRAM_ONLY`.

### 7.7 `gfx_line`

Рисует произвольную линию алгоритмом Bresenham.

`GfxLine`:

```text
offset size field
0      2    x0
2      1    y0
3      2    x1
5      1    y1
6      1    color
7      1    flags
```

Требования:

- горизонтальные и вертикальные случаи перенаправлять в ускоренные функции;
- диагональный путь может использовать CPU;
- обычный вариант проверяет обе конечные точки и не выполняет clipping;
- приоритет реализации ниже тайлов, палитры и прямоугольных операций.

### 7.8 Предусловия быстрых вариантов

Любая функция с суффиксом `_fast` принимает только полностью проверенные
координаты и длины. Нарушение предусловий может не просто испортить пиксели:
запись за 320 байт выбранной строки способна перезаписать соседний экранный
буфер, дескрипторы экранных ячеек и палитровые регистры. Это предупреждение
должно присутствовать рядом с каждой публичной `_fast` сигнатурой.

## 8. Копирование и аппаратное зеркало

### 8.1 Идентификаторы экранных областей

Источник копирования задаётся отдельно:

```text
GFX_SRC_BUFFER0
GFX_SRC_BUFFER1
GFX_SRC_FRONT
GFX_SRC_BACK
```

Источник всегда читается из DRAM-зеркала соответствующего буфера.

Назначение задаётся обычными флагами `GFX_DST_*`, `VRAM_ONLY`, `KEY_FF`.

### 8.2 Дескриптор `GfxCopyRect`

```text
offset size field
0      1    source_buffer
1      1    destination_flags
2      2    source_x
4      1    source_y
5      2    destination_x
7      1    destination_y
8      2    width
10     2    height
```

Координаты X — `u16`, Y — `u8`, размеры — `u16`. Обычный entry проверяет обе
области целиком; выход источника или назначения за экран возвращает
`GFX_ERR_ARGUMENT` без копирования.

### 8.3 `gfx_copy_rect`

```text
gfx_copy_rect(copy_descriptor)
```

Поддерживает:

- buffer 0 → buffer 1;
- buffer 1 → buffer 0;
- копирование внутри одного буфера;
- разные координаты источника и назначения;
- копирование в front/back;
- обновление зеркала назначения или `VRAM_ONLY`;
- прозрачное копирование байтов `#FF`;
- проверку полного нахождения источника и назначения на экране.

Копирование выполняется построчно горизонтальным `COPY`. Если Y источника и
назначения различаются, для каждой строки:

1. установить `PORT_Y=source_y` и выполнить фазу чтения;
2. установить `PORT_Y=destination_y` перед фазой записи;
3. непосредственно после фазы записи выполнить `LD B,B`.

`COPY_VERT` для этого не применяется: он не позволяет независимо выбрать Y
двух фаз. Выбор «вертикально или горизонтально» допустим для заливок, но не
является общей эвристикой копирования.

Копирование перекрывающихся областей внутри одного зеркала должно иметь
семантику `memmove`. До реализации обратного аппаратного прохода допускается
статический построчный буфер DLL размером 320 байт. Размещать его на стеке
запрещено.

### 8.4 `gfx_copy_buffer`

```text
gfx_copy_buffer(source_buffer, destination_flags)
```

Копирует все 320×256 пикселей из зеркала исходного буфера в выбранное
назначение.

Типичное применение:

- подготовить второй экран перед включением double buffering;
- синхронизировать чистый фон buffer 0 и buffer 1;
- скопировать видимый чистый фон в back buffer.

### 8.5 `gfx_restore_background_rect`

```text
gfx_restore_background_rect(target, x, y, width, height)
```

`GfxRestoreRect`:

```text
offset size field
0      2    x
2      1    y
3      2    width
5      2    height
7      1    target
```

Копирует:

```text
DRAM mirror target → VRAM target
```

по тем же координатам.

Функция:

- не выбирает отдельный источник;
- не меняет зеркало;
- не применяет прозрачность;
- используется для стирания временных спрайтов;
- поддерживает buffer 0/1/front/back;
- отвергает область, не помещающуюся на экране.

Для копирования зеркала одного экрана в другой используется `gfx_copy_rect`.

### 8.6 `gfx_move_rect` и `gfx_scroll_rect`

`gfx_move_rect` — позднее имя для `gfx_copy_rect` с обязательной
`memmove`-семантикой внутри одного буфера. `GfxMoveRect` использует layout
`GfxCopyRect`; источник и назначение должны указывать на один и тот же буфер.

`gfx_scroll_rect` сдвигает содержимое ограниченной области на знаковые `s16 dx/dy`
и заполняет освободившиеся полосы цветом. `GfxScrollRect`:

```text
offset size field
0      2    x
2      1    y
3      2    width
5      2    height
7      2    dx
9      2    dy
11     1    fill_color
12     1    flags
13     3    reserved = 0
```

Обе функции читают источник из DRAM-зеркала. Изменения, сделанные ранее через
`VRAM_ONLY`, в переносимое содержимое не входят.

## 9. Палитра

### 9.1 Формат

Базовый формат — 256 последовательных RGB8-троек:

```text
R0,G0,B0, R1,G1,B1, ... R255,G255,B255
```

Размер — 768 байт.

### 9.2 Маска палитровых банков

```text
bit 0 GFX_PAL_BUFFER0
bit 1 GFX_PAL_BUFFER1

GFX_PAL_BOTH = 3
```

Нулевая маска считается ошибкой.

По умолчанию приложения должны обновлять обе палитры, чтобы переключение
экранных буферов не меняло цвета.

### 9.3 `gfx_palette_load256`

```text
gfx_palette_load256(source, palette_mask)
```

Требования:

- сначала скопировать 768 байт во внутренний буфер, пока исходный указатель
  гарантированно доступен;
- затем записать 256 RGB8-цветов прямым портовым циклом;
- не использовать 256/512 вызовов BIOS;
- обновить выбранные палитровые банки;
- сохранить базовую палитру во внутреннем буфере библиотеки;
- установить текущий fade-level в 32;
- сохранить и восстановить CPU-окно;
- завершить с `PORT_Y=#C0`.

Вызов во время активного fade возвращает `GFX_ERR_BUSY`. Вызывающий должен
сначала выполнить `gfx_fade_cancel`.

### 9.4 `gfx_palette_load_range`

```text
gfx_palette_load_range(first, count, source, palette_mask)
```

Регистровый ABI:

```text
DE = source
A  = first
IX = count_mask

count        = IX & #01FF
palette_mask = (IX >> 9) & #03
bits 11..15  = 0
```

Требования:

- диапазон не должен выходить за индекс 255;
- `count=0` означает пустую операцию;
- обновить аппаратную и внутреннюю базовую палитру;
- не изменять остальные цвета.

Вызов во время активного fade возвращает `GFX_ERR_BUSY`.

### 9.5 `gfx_palette_set`

```text
gfx_palette_set(index, r, g, b, palette_mask)
```

Регистровый ABI:

```text
A   = index
D   = r
E   = g
IXL = b
IXH = palette_mask
```

Изменяет один цвет в аппаратной и сохранённой базовой палитре.

Вызов во время активного fade возвращает `GFX_ERR_BUSY`.

### 9.6 Внутренний буфер палитры

Библиотека хранит:

- `base_palette[768]`;
- `palette_lut[256]`;
- флаг наличия базовой палитры;
- текущий уровень яркости;
- состояние fade.

Такой кэш позволяет выполнять fade после отключения или переподключения
страницы, в которой находился исходный ресурс.

### 9.7 Общий код с будущим GFX640

Палитра не выносится в отдельную runtime-DLL: иначе пришлось бы дублировать
управление окнами и координировать fade/swap через два libman handle.

Реализация палитры, fade, window manager и макросы акселератора оформляются как
общие исходные include-модули, например:

```text
common/palette.inc
common/fade.inc
common/winmgr.inc
common/accelerator.inc
```

Они включаются при сборке `GFX320.DLL` и будущего `GFX640.DLL`. Публичные
сигнатуры и номера палитровых entry `13..20` должны совпадать, хотя runtime
каждой библиотеки остаётся монолитным.

## 10. Fade-in и fade-out

### 10.1 Модель яркости

Используется 33 уровня:

```text
0  = чёрный
32 = исходная палитра
```

Для уровня `level`:

```text
LUT[c] = round(c * level / 32)
```

LUT строится один раз на уровень, затем применяется ко всем 768 компонентам
базовой палитры.

### 10.2 `gfx_fade_begin`

```text
gfx_fade_begin(direction, duration_frames, palette_mask)
```

Направления:

```text
GFX_FADE_OUT: level 32 → 0
GFX_FADE_IN:  level 0  → 32
```

Требования:

- базовая палитра должна быть загружена;
- если другой fade уже активен, вернуть `GFX_ERR_BUSY`;
- `duration_frames=0` немедленно применяет конечное состояние;
- состояние fade хранится внутри DLL;
- в один момент активен один fade;
- функция не запускает собственный цикл ожидания кадров.

### 10.3 `gfx_fade_step`

Применяет один шаг и возвращает признак продолжения:

```text
A = 0 — успех
E = 1, если fade ещё активен
E = 0, если достигнуто конечное состояние
```

Функция:

- не ждёт кадрового события;
- не вызывает музыкальный проигрыватель;
- гарантирует точное достижение уровней 0 или 32;
- распределяет 32 уровня по указанному числу кадров аккумулятором, без
  накопления ошибки.

Рекомендуемый игровой цикл:

```text
if frame_counter != consumed_frame:
    consumed_frame = frame_counter
    gfx_swap_buffers      ; при необходимости
    gfx_fade_step

update_input
update_audio
```

### 10.4 `gfx_fade_cancel`

Останавливает fade, оставляя текущую аппаратную палитру без изменений.

### 10.5 Контракт кадров

`duration_frames` означает число вызовов `gfx_fade_step`, выполненных по
разным кадровым событиям приложения. GFX320 не проверяет происхождение события
и не содержит блокирующих `gfx_fade_in/gfx_fade_out`.

## 11. Формат тайлов

### 11.1 Размер

Базовый и единственный обязательный размер тайла — 16×16 пикселей.

Преимущества:

- 256 байт на тайл;
- 64 тайла точно заполняют страницу 16 КБ;
- адрес вычисляется без умножения;
- высота 16 выгодна для акселератора;
- экран образует сетку 20×16;
- 32×32 представляется metatile 2×2 без дублирования формата.

Тайл 24×24 не поддерживается основным форматом из-за неудобной адресации и
несовпадения с геометрией экрана.

### 11.2 Row-major layout

Обязательный формат ABI 1.0 — row-major: каждая строка хранится непрерывно.

```text
tile + #00: Y=0,  X=0..15
tile + #10: Y=1,  X=0..15
...
tile + #F0: Y=15, X=0..15
```

Один тайл:

```text
16 rows × 16 bytes = 256 bytes
```

Вывод выполняется шестнадцатью горизонтальными `COPY` по 16 байт с установкой
`PORT_Y` для каждой строки. Это проверенный путь из `spevosdk/lib_tiles.asm` и
`lib_sprites.asm`.

Column-major не объявляется «невозможным»: двухфазная схема
`COPY source→accelerator RAM`, затем `COPY_VERT accelerator RAM→VRAM`
работает в AFNT320. Но она требует двух фаз с переключением режима на колонку
и не является
прямым вертикальным чтением DRAM. В ABI 1.0 этот layout не поддерживается;
этап 9 может сравнить обе схемы на железе и добавить новый явно помеченный
формат только при измеримом выигрыше.

### 11.3 Страница тайлов

16-КБ страница содержит только pixel payload:

```text
offset #0000: tile 0
offset #0100: tile 1
...
offset #3F00: tile 63
```

Заголовки, таблицы и маски не размещаются внутри страницы, иначе теряется
точное заполнение 64 тайлами.

### 11.4 Таблица физических страниц

DSS выделяет физические страницы динамически. Приложение передаёт библиотеке
таблицу:

```text
logical page index → physical DSS page
```

Функция:

```text
gfx_set_page_table(source, page_count)
```

должна скопировать номера во внутренний массив DLL.

```text
DE = source
IX = page_count, 1..256
```

Требования:

- максимум 256 логических страниц;
- `page_count=0` возвращает `GFX_ERR_ARGUMENT`;
- до установки таблицы тайловые функции возвращают `GFX_ERR_PAGE`;
- изменение исходной таблицы после вызова не влияет на DLL;
- физический номер страницы никогда не хранится непосредственно в tilemap.

Рекомендуемый путь получения таблицы приложением:

1. `DSS GETMEM #3D` выделяет блок из нужного числа 16-КБ страниц;
2. `BIOS EMM_FN5 / GETMEMBLKPAGES #C5` возвращает массив физических номеров;
3. этот массив передаётся в `gfx_set_page_table`.

Физические страницы одного DSS-блока могут быть несмежными. Поэтому
арифметическое `first_page + logical_page` запрещено; O(1)-таблица
logical→physical является обязательной частью дизайна.

### 11.5 `TileRef`

Ссылка занимает 16 бит:

```text
TileRef = (logical_page << 8) | tile_slot
```

Ограничения:

```text
logical_page: 0..page_count-1
tile_slot:    0..63
```

В регистрах:

```text
D = logical_page
E = tile_slot
```

В little-endian памяти:

```text
byte 0 = tile_slot
byte 1 = logical_page
```

O(1)-разрешение:

```text
physical_page = page_table[D]
OUT #82, physical_page
address = E * #100
```

При фиксированном source window WIN0:

```text
H = E
L = #00
```

Глобальный номер тайла может быть преобразован инструментом упаковки:

```text
logical_page = global_tile >> 6
tile_slot    = global_tile & 63
```

## 12. Тайловый API

### 12.1 `gfx_draw_tile`

Рекомендуемый горячий ABI:

```text
DE = TileRef
IX = X в пикселях
IYH = 0
IYL = Y в пикселях
A  = destination/write flags
```

Требования:

- разрешить логическую страницу через внутреннюю page table;
- проверить слот `0..63`;
- проверить `X<=304`, `Y<=240`; иначе вернуть `GFX_ERR_ARGUMENT` без записи;
- использовать row-major: до 16 горизонтальных `COPY`;
- при `KEY_FF` выбрать страницу `#58` или `#5C`;
- восстановить CPU-окна и `PORT_Y`.

`gfx_draw_tile` и `gfx_draw_tile_fast` имеют один формат тайла и один
регистровый ABI. Они различаются только наличием проверок.

### 12.2 `gfx_draw_tile_fast`

Предусловия:

- `0 <= X <= 304`;
- `0 <= Y <= 240`;
- логическая страница существует;
- слот `0..63`;
- зарезервированные биты флагов равны нулю.

Функция минимизирует проверки и переходы.

### 12.3 `gfx_draw_tile_clip`

Медленный вариант одиночного тайла. Координаты всё равно должны быть внутри
экрана: `X<=319`, `Y<=255`. Функция обрезает только правый и/или нижний свес:

- справа уменьшается длина горизонтального блока каждой строки;
- снизу уменьшается число выводимых строк;
- source всегда начинается с первой строки и первого байта тайла;
- отрицательных координат и top/left clipping в ABI 1.0 нет.

Полностью видимый тайл перенаправляется во внутренний обычный tile-loop.

### 12.4 `gfx_draw_tile_span`

```text
gfx_draw_tile_span(tile_refs, count, x, y, flags)
```

Рисует горизонтальную последовательность тайлов.

`GfxTileSpan`:

```text
offset size field
0      2    tile_refs
2      2    count
4      2    x
6      1    y
7      1    flags
```

Полный размер `GfxTileSpan` равен 8 байтам; у этой структуры нет
зарезервированного хвоста. Это отличается от `GfxFillRect` и `GfxTileList`,
размеры которых включают явно указанные поля `reserved`.

Требования:

- назначение и `RGMOD` вычисляются один раз;
- каждая очередная `TileRef` читается до подключения WIN0/VRAM;
- каждый тайл является отдельной DI-секцией с восстановлением обоих окон;
- текущая физическая source page кэшируется, чтобы не повторять разрешение
  logical page через page table;
- X увеличивается на 16;
- `count=0` — успешная пустая операция;
- вся полоса должна помещаться на экране: `x + count*16 <= 320`, `y<=240`;
  иначе обычный entry возвращает `GFX_ERR_ARGUMENT`.

### 12.5 `gfx_draw_tilemap`

`GfxTilemap`:

```text
offset size field
0      2    tile_refs
2      2    map_width
4      2    map_height
6      2    source_tile_x
8      2    source_tile_y
10     2    draw_width
12     2    draw_height
14     2    destination_x
16     1    destination_y
17     1    flags
18     2    reserved = 0
```

Требования:

- TileRef имеет размер 2 байта;
- поддерживать вывод прямоугольного окна из большой карты;
- кэшировать разрешённый physical page, не оставляя WIN0 подключённым;
- проверять границы source-окна карты и полное размещение результирующей
  сетки тайлов на экране;
- не вызывать публичный `gfx_draw_tile` через libman для каждого элемента;
- использовать внутренний быстрый tile loop.

`destination_x/y` задают верхний левый пиксель целого тайла. ABI 1.0 не
выполняет partial-tile clipping карты, поэтому края окна кратны 16 пикселям.
Плавный попиксельный scroll большой карты требует будущего
`gfx_draw_tilemap_clip`: быстрой середины и отдельных медленных кромок. Такая
функция не входит в ABI 1.0; `source_tile_x/y` обеспечивают scroll шагом в
один тайл.

В ABI 1.0 `tile_refs` — обычный CPU pointer. Descriptor копируется целиком до
первого mapping. Перед каждым тайлом библиотека читает соответствующую
`TileRef` в scratch, затем выполняет атомарный tile-loop по §15. Поэтому массив
может находиться в окне, временно используемом как VRAM, но не в постоянно
недоступной памяти.

Paged tilemap является отдельным расширением этапа 6: одна и та же source
window попеременно подключает страницу карты и страницу пикселей. Каждое такое
переключение инвалидирует page cache тайлов; формат ссылки на карту и цена
переключений должны быть отдельно специфицированы и измерены до добавления в
ABI.

### 12.6 `gfx_draw_metatile`

Metatile — прямоугольная композиция TileRef, обычно 2×2.

Функция принимает:

```text
offset size field
0      2    tile_refs
2      1    width_in_tiles
3      1    height_in_tiles
4      2    x
6      1    y
7      1    flags
```

32×32 ассет задаётся четырьмя ссылками 16×16. Pixel payload не дублируется.
Массив `tile_refs` подчиняется тому же правилу поэлементного prefetch, что span
и resident tilemap.

`width_in_tiles=0` или `height_in_tiles=0` — успешная пустая операция.
Обычный entry требует, чтобы metatile целиком помещался на экране.

### 12.7 `gfx_draw_tile_list`

Пакетный вывод произвольно расположенных тайлов устраняет повторную стоимость
`l_call`, настройки назначения и подключения VRAM для каждого спрайта:

```text
gfx_draw_tile_list(DE = &GfxTileList)
```

`GfxTileList`:

```text
offset size field
0      2    items
2      2    count
4      1    flags
5      3    reserved = 0
```

Каждый `GfxTileItem` занимает 5 байт:

```text
offset size field
0      2    TileRef
2      2    x
4      1    y
```

Требования:

- `count=0` — успешная пустая операция;
- назначение, VRAM alias и `RGMOD` вычисляются один раз на список;
- все элементы требуют `x<=304`, `y<=240`; частичный тайл выводится отдельным
  вызовом `gfx_draw_tile_clip`;
- флаги общие для списка; смешанный opaque/keyed вывод делится вызывающим на
  два списка;
- resolved physical page кэшируется; библиотека не сортирует items, а
  вызывающему рекомендуется группировать их по `logical_page`;
- каждый пятибайтовый item полностью читается в scratch до подключения
  WIN0/VRAM; массив может лежать в временно перекрываемом VRAM window;
- каждый элемент выполняется как отдельная ограниченная DI-секция;
- внутренний цикл не вызывает публичный entry на каждый элемент.

### 12.8 Прозрачные строки

Опциональное расширение формата метаданных:

```text
u16 nonempty_rows на тайл
```

Бит 15 соответствует Y=0, бит 0 — Y=15.

Полностью состоящая из `#FF` строка при keyed-выводе может быть пропущена без
запуска акселератора. Маски хранятся отдельно от 16-КБ pixel pages.

Расширение реализуется только после benchmark, подтверждающего выигрыш с учётом
дополнительного чтения маски.

## 13. Инструмент упаковки тайлов

Необходим host-side инструмент, например `tools/tilepack.py`.

Вход:

- PNG/BMP с индексированной 256-цветной графикой;
- ширина и высота, кратные 16;
- опциональный прозрачный индекс;
- порядок тайлов: слева направо, сверху вниз.

Выход:

- `pageNN.bin` размером ровно 16 384 байта;
- row-major тайлы по 256 байт;
- TileRef-таблица;
- описание количества логических страниц;
- опциональные `nonempty_rows`;
- палитра RGB8 на 768 байт;
- отчёт о числе тайлов, страницах и заполнении последней страницы.

Последняя неполная страница дополняется:

- `#FF` для keyed-набора;
- `#00` для непрозрачного набора;
- тип дополнения фиксируется в manifest.

Инструмент обязан:

- проверять 8bpp/indexed вход;
- запрещать больше 64 тайлов в одной странице;
- сохранять row-major порядок строк без runtime-транспонирования;
- проверять byte-exact round-trip тайлов в тестах;
- генерировать TileRef без физических DSS-страниц;
- уметь сформировать metatile/tilemap из исходной сетки.

Runtime не выполняет преобразование формата.

Ориентировочный постоянный объём данных:

```text
page table:      256 bytes
base palette:    768 bytes
fade LUT:        256 bytes
row buffer:      320 bytes
state/scratch:   менее 160 bytes
total:           около 1.7 KB
```

Построчный буфер для `memmove` является статическим. Большие временные буферы
на стеке запрещены. Отдельного внутреннего стека и переключения `SP` нет.

В формате DLL нет отдельной BSS-секции, не занимающей место в памяти:
вся статика вместе с кодом входит в загружаемый 16-КБ префикс. RLE уменьшает
только файл на диске, но не runtime image. Сборка использует
`sprinter-mkdll` и проверяет размер образа и таблицы релокаций.

## 15. Безопасность аппаратного состояния

Обычная операция, использующая только VRAM window, должна:

1. скопировать descriptor в scratch DLL;
2. проверить, что текущий `SP` не находится в VRAM window;
3. сохранить входное состояние maskable interrupts и выполнить `DI`;
4. сохранить и подключить VRAM page;
5. выполнить ограниченную группу аппаратных операций;
6. завершить каждую блочную процедуру непосредственным `LD B,B`;
7. установить `PORT_Y=#C0`, восстановить VRAM page;
8. выполнить `EI` только если прерывания были разрешены до вызова.

Тайловая операция использует WIN0 как фиксированное source window. Её
атомарная единица — один тайл:

1. до `DI` прочитать `TileRef`, разрешить physical page, скопировать
   координаты, флаги и остальные данные тайла в регистры/scratch;
2. проверить VRAM window относительно DLL и текущего `SP`;
3. сохранить входное состояние interrupts и выполнить `DI`;
4. сохранить страницы WIN0 и VRAM;
5. подключить физическую страницу тайлов в WIN0 и VRAM alias в VRAM window;
6. вывести до 16 row-major строк тайла, завершая блочную процедуру каждой
   строки непосредственным `LD B,B`;
7. убедиться, что последняя строка также завершена `LD B,B`;
8. установить `PORT_Y=#C0`, восстановить сначала VRAM, затем WIN0;
9. восстановить входное состояние interrupts.

До шага 3 реализация также проверяет, что DLL и текущий `SP` не находятся в
WIN0. Это предотвращает выборку инструкций или обращение к стеку из временно
подменённой source page.

В пакетных функциях этот цикл повторяется для каждого тайла. Внешний `l_call`,
разбор descriptor, назначение и `RGMOD` остаются общими, но при `EI` оба окна
уже восстановлены. Это ограничивает задержку ISR временем одного тайла и не
требует внутреннего стека.

Контракт приложения:

- код вне GFX320 не оставляет собственную команду акселератора или активный
  `ACC_MODE` незавершёнными перед вызовом библиотеки;
- обычный стек программы не находится в выбранном VRAM window;
- ISR не должен менять `PORT_Y`, page registers или состояние акселератора
  одновременно с GFX320.

Нельзя:

- возвращаться из функции с активным `ACC_MODE`, выбранным самой GFX320;
- возвращаться с видимым значением `PORT_Y`;
- подключать VRAM поверх DLL;
- читать следующую команду или данные из окна, которое временно заменено VRAM;
- выполнять длинный tilemap как одну общую DI-секцию.

Пока source page подключена в WIN0:

- maskable interrupts запрещены на всё время mapping;
- запрещены `RST #08`, `RST #10` и любые BIOS/DSS-вызовы;
- запрещено исполнять код или читать таблицы из WIN0;
- WIN0 восстанавливается до `EI`, потому что скрыты системные векторы IM1/IM2
  и BIOS;
- приложение гарантирует отсутствие NMI на всё время mapping, поскольку
  `#0066` также скрыт. `DI` не блокирует NMI, поэтому это отдельное обязательное
  предусловие, а не следствие запрета maskable interrupts.

Build-time параметр `GFX_DI_BUDGET_US` по умолчанию равен 200 мкс. Benchmark
на реальном Sprinter обязан подтвердить, что вывод худшего одиночного тайла и
каждая группа palette/copy укладываются в бюджет. Если тайл превышает бюджет,
реализация оптимизируется или бюджет явно пересматривается; делить один тайл
с `EI` при подключённом WIN0 запрещено.

## 16. Тестирование

### 16.1 Host-тесты

Обязательные автоматические проверки:

- byte-exact row-major упаковка 16×16;
- 64 тайла занимают ровно 16 КБ;
- `TileRef` правильно разрешается для всех page/slot;
- неверный slot `64..255` отвергается;
- `page_count=0` отвергается, `page_count=256` принимается;
- safe-функции отвергают выход по правой/нижней границе до первой записи;
- `gfx_draw_tile_clip` корректно обрабатывает только правый и нижний свес;
- `gfx_copy_rect` согласованно отвергает выход источника и назначения;
- обработка нулевых размеров;
- ABI size/offset каждого descriptor и упаковка регистровых аргументов;
- byte-exact совпадение смещений descriptor в `gfx320.inc`, `gfx320.h` и
  Pascal-unit с одним машинно читаемым эталоном;
- определение code/stack window для всех старших байтов адреса;
- отказ при попадании `SP` в выбираемое VRAM window;
- `source_window=0`, восстановление WIN0/VRAM и исходного состояния interrupts
  на всех путях ошибки;
- fade LUT для уровней `0`, `1`, `16`, `31`, `32`;
- точные конечные значения fade;
- palette range не выходит за индекс 255.

### 16.2 Тестовый EXE

MVP-профиль `GFX320.EXE` после этапа 3 должен:

- включать режим `#81` для обоих экранов;
- настроить тестовую палитру через BIOS/приложение, если optional этап 4 ещё не
  реализован;
- очищать выбранный буфер;
- рисовать fill-rect, горизонтальные и вертикальные линии;
- проверять правую часть X=`256..319`;
- показывать непрозрачные и keyed-тайлы;
- выводить `gfx_draw_tile_span` и `gfx_draw_tile_list`;
- проверять восстановление WIN0 и работу кадрового/звукового ISR между
  тайлами;
- ожидать клавишу перед завершением;
- восстанавливать исходный видеорежим.

Post-MVP профиль по мере реализации этапов 4–8 дополнительно должен:

- загружать палитру через GFX320;
- рисовать рамки и произвольные линии;
- выводить тайл с правым и нижним свесом через `gfx_draw_tile_clip`;
- переключать buffer 0/1;
- копировать прямоугольник между экранами;
- рисовать VRAM-only объект и восстанавливать фон из зеркала;
- установить собственный кадровый ISR/frame counter для fade, не передавая
  владение прерываниями библиотеке;
- выполнять fade-out и fade-in вызовами `gfx_fade_step` по кадровому счётчику;
- восстановить исходный обработчик прерывания.

### 16.3 Проверка на реальном Sprinter

Обязательно проверить:

- `#50`, `#54`, `#58`, `#5C`;
- прозрачность `#58` с обновлением зеркала;
- отсутствие transient-спрайтов в mirror-source;
- restore mirror→VRAM;
- обе аппаратные палитровые банки;
- fade без цветовых выбросов при swap;
- отсутствие мусора после возврата `PORT_Y=#C0`;
- работу X=`319`;
- работу высоты 256 через аппаратный count=0;
- отсутствие записи в `#280..#3FF` на граничных значениях safe/clip
  примитивов;
- row-major вывод тайла обычными горизонтальными `COPY`;
- отдельно, как эксперимент, двухфазный column-major
  `COPY`→internal buffer→`COPY_VERT`;
- максимальную длительность каждой DI-секции;
- восстановление исходной страницы WIN0 после каждого одиночного и пакетного
  тайла;
- отсутствие `RST`/BIOS/DSS-вызовов, пока WIN0 содержит страницу тайлов;
- выполнение NMI-контракта: источник NMI отсутствует на время tile-loop;
- взаимодействие с прерываниями и звуковым проигрывателем.

Старый MAME может неверно эмулировать `#58`, поэтому реальное железо является
эталоном для этой комбинации.

### 16.4 Benchmark

Измерить:

- очистку полного буфера;
- fill-rect нескольких размеров и обеих ориентаций;
- один opaque tile;
- один keyed tile;
- один `gfx_draw_tile_clip` с правым/нижним свесом;
- row-major и экспериментальный двухфазный column-major путь одного тайла;
- 20×16 tilemap;
- 32 отдельных `gfx_draw_tile` против одного `gfx_draw_tile_list` из 32
  элементов;
- стоимость атомарного tile-loop, включая сохранение/подключение/восстановление
  WIN0 и VRAM;
- copy buffer 0→1;
- restore 16×16;
- полную загрузку палитры;
- один fade-step.

Результаты должны храниться в отдельном документе с указанием частоты CPU,
версии DSS и типа платформы: реальный Sprinter или эмулятор.

## 18. Порядок фиксации ABI

До завершения этапа 0 номера libman entry могут изменяться. В конце этапа 0
фиксируются форма таблицы, management/introspection entry `0..5`, общая модель
ошибок, беззнаковая модель координат, отсутствие `GFX_CLIP`, фиксированный
source WIN0 и ограничения `l_call`.

После этапа 1 фиксируются:

- номера базовых примитивов;
- destination flags;
- `GfxFillRect` и регистровый ABI `gfx_hline/gfx_vline`;
- политика safe/fast и предупреждения о записи за строку.

После этапа 2 фиксируются:

- `TileRef`;
- регистровый ABI `gfx_set_page_table` и формат page table;
- row-major tile layout;
- ABI обычного/fast одиночного тайла;
- атомарный WIN0 tile-loop.

После этапа 3 фиксируются `GfxTileSpan`, `GfxTileList` и обязательный ABI MVP.

После этапа 4 фиксируется регистровый ABI palette-entry `13..15`. После этапа
5 фиксируется copy-descriptor. После этапа 6 фиксируются
`gfx_draw_tile_clip`, `GfxTilemap` и `GfxMetatile`. После этапа 7 фиксируются
fade-entry `16..20`; номера и сигнатуры `13..20` становятся общими для
GFX320/GFX640.

После этапа 8 публичный ABI версии 1.0 считается замороженным. Этап 9 может
менять только внутреннюю реализацию и добавлять новые функции в конец таблицы;
экспериментальный column-major путь не меняет формат ABI 1.0.

- `gfx320.inc` для sjasmplus: номера entry, `GFX_ERR_*`, флаги,
  capabilities и смещения всех descriptor;
- `gfx320.h`, `gfx320.lib` и совместимый с `sdasz80` shim libman для
  SDCC 2.9.0;
- тонкий `GFX320.INC` для обновлённого Turbo Pascal поверх
  `lib_pas/LIBMAN.INC`;
- ASM-, C- и Pascal-примеры;
- `GFX320.DLL`, `GFX320.EXE`, tile packer, host-тесты и benchmark.

Shim libman для SDCC — самостоятельный deliverable этапа 1, а не скрытая часть
финальной оптимизации. Публичные include/header генерируются из одного
машинно читаемого описания ABI либо проверяются друг против друга byte-exact
host-тестом.

Отдельная страница для конкретного SOLID C `loaddll/calldll/freedll` не является
обязательной, пока такой клиент не найден в проверяемом дереве toolchain.
Если он будет добавлен, адаптер заполняет только гарантированные
`A/DE/IX/IY`, проверяет результат `A` и не полагается на `CF`.

### 19.2 SDCC 2.9.0

C-API скрывает регистровые упаковки `length_flags/count_mask` и предоставляет
плоские сигнатуры. Возвращаемое значение C-функции — только код ошибки;
`gfx_get_pixel`, `gfx_fade_step`, `gfx_get_version` возвращают данные через
out-pointer.

Структуры в `gfx320.h` состоят только из `u8/u16`, без `long`, bit fields и
неявного выравнивания. Компиляционный тест проверяет каждый `sizeof/offsetof`.
Descriptor, `TileRef[]` и `GfxTileItem[]` размещаются в `_DATA/_BSS`, а не в
`static const`: SDCC помещает const-данные в `_CODE`, которое приложение может
разрешить перекрывать. Физические номера страниц получаются рекомендованной
цепочкой `dss_getmem()` → `bios_emm_list()`; страницы блока не считаются
физически смежными.

### 19.3 Turbo Pascal

Актуальный `LIBMAN.INC` не является старым прямым `JP base+#20+3*fn`
клиентом. Он загружает L0/L1 сам, маршалирует `LibRegA/DE/IX/IY`, намеренно
отбрасывает flags обычного DLL-entry и хранит manager error в отдельном
`LibErr`. Binding проверяет сначала boolean-результат `LibCall`, затем
`LibRegA`.

TPC не гарантирует удобный packed-record ABI, поэтому descriptor описываются
как `array[0..N] of byte` с константами смещений, сгенерированными из того же
эталона, что `gfx320.inc`. Include остаётся тонким: длинные графические циклы
в Pascal-binding не дублируются.

### 19.4 Канонические раскладки

| Клиент | Обычная память клиента | DLL | Рекомендуемая конфигурация |
|---|---|---|---|
| SDCC compact `CODE_LOC=0x8100` | WIN2: code+data+stack | WIN3 | source=WIN0, VRAM=WIN1 |
| SDCC default/extended | сверять с linker map; обычно WIN1+WIN2 | WIN3 | source=WIN0; VRAM — окно из WIN1/WIN2 без текущего `SP` |
| TPC `/D:8000` | программа и stack ниже `#8000` | WIN3 | source=WIN0, VRAM=WIN2 |
| TPC default | WIN1+WIN2, stack ниже `#C000` | WIN3 | source=WIN0; обычно VRAM=WIN1 |

Таблица является рецептом, а не автоматическим детектором: приложение
проверяет собственную linker map и отсутствие NMI во время tile-loop.
Выбранное VRAM window и фиксированный WIN0 source читаются через
`gfx_get_config`.

## 20. Критерий полной готовности

Полная версия считается готовой, когда:

- поддерживает все функции этапов 0–9;
- работает в режиме DSS `#81` на обоих экранных буферах;
- корректно управляет четырьмя режимами записи `#50/#54/#58/#5C`;
- выполняет O(1)-поиск тайла по `TileRef`;
- выводит opaque и keyed tilemap;
- загружает полную RGB8-палитру прямой записью;
- выполняет плавные fade-in/fade-out;
- копирует чистый фон между экранами;
- восстанавливает VRAM из аппаратного зеркала;
- имеет тестовый EXE, host-тесты, benchmark и документацию;
- прошла проверку на реальном Sprinter.

# WIN320.DLL — техническое задание

## 1. Назначение

`WIN320.DLL` — библиотека простого оконного интерфейса для компьютера Sprinter
в графическом режиме DSS `#81` (320×256×256). Она не является всеобъемлющим
GUI-фреймворком: цель — дать приложению набор готовых блоков, из которых
строится интерфейс в стиле GFX Viewer / Flex Navigator.

Библиотека предоставляет:

- отрисовку окон с 3D-панелями и рамками (raised/sunken);
- контролы: лейбл, кнопка, checkbox, radio button, поле ввода
  (редактирование), listbox, прогрессбар, скроллбар, иконка, разделители,
  инверсия выделения;
- два способа построения интерфейса:
  - декларативно, по списку объектов окна (аналог `MakeWindow` из FN API);
  - прямым вызовом отдельного контрола — с тем же самым дескриптором, что
    стоит в списке, для точечной перерисовки и обновления;
- перерисовку только изменившихся объектов (флаг `WIN_IT_DIRTY` +
  `win_update`);
- цветовые роли в одной таблице темы (`win_set_theme`);
- модальные окна с сохранением/восстановлением фона;
- опрос мыши и клавиатуры: неблокирующий `win_poll` и блокирующий
  `win_track`, возвращающие управление по нажатию кнопок мыши над объектом,
  по горячей клавише или по любой нажатой клавише (с сырым скан-кодом);
  Tab-обход фокуса между контролами;
- работу с экраном 0 или экраном 1 (настраивается).

Прототипы поведения: `gfxview` (`gfx_wind.asm`, `gfx_ms.asm`, `gfx_prt.asm`)
и Flex Navigator API v0.4 (`flexnavigator/plugins/fn_api_0.4.txt`).
Соответствие FN API приведено в §17. Соглашения об относительных
координатах, ролях темы и кодах событий согласованы с текстовой
UI-библиотекой того же семейства `sources/ui_lib` (§22).

Библиотека использует ABI libman 1.2/1.3 и собирается в формате L0
инструментом `sprinter-mkdll`. Рабочее имя файла — `WIN320.DLL`, каталог
модуля — `win320/`. Для режима 640×256 будет отдельная библиотека `WIN640`
с совпадающими номерами entry.

### 1.1 Типовой сценарий клиента

Декларативный путь намеренно короткий:

1. приложение включает DSS-режим `#81`, загружает DLL в рекомендуемое
   окно **WIN3** и вызывает `win_style`; встроенный шрифт уже загружен
   `win_init` из хвоста DLL;
2. контролы описываются обычными packed-структурами, ссылки на них
   собираются в `WinItem[]`, а массив — в `WinWindow`;
3. постоянное окно рисуется `win_draw`, модальный диалог открывается
   `win_open`;
4. цикл вызывает `win_poll` или `win_track`; по событию приложение меняет
   только своё состояние контрола, ставит `WIN_IT_DIRTY` и вызывает
   `win_update`;
5. модальный диалог закрывается `win_close`, затем приложение вызывает
   `l_free` (он сам вызывает `win_free`) и освобождает переданные
   backstore-страницы. Страницу шрифта освобождает сама DLL.

Для небольшого императивного экрана массивы не нужны: приложение задаёт
начало отсчёта и вызывает `win_panel`, `win_label`, `win_button` и другие
entry напрямую. Дескрипторы в обоих путях одинаковы; callbacks и
объектная runtime-модель отсутствуют.

## 2. Границы первой версии

Поддерживается только режим DSS `#81`: 320×256, 8 бит/пиксель, строка
320 байт, два экранных буфера, физическая строка VRAM 1024 байта
(экран 0 — смещение `#000`, экран 1 — смещение `#140` внутри строки).

Обязательный MVP — этапы 0–3 (§19):

- инициализация, конфигурация, выбор экрана, тема, формат строк;
- автоматическая загрузка встроенного шрифта из хвоста DLL в отдельную
  EMM-страницу; замена шрифта из файла через `win_load_font` (§3.6);
- примитивы: заливка, рамка, панель, разделители, инверсия;
- текст: лейбл (через общее текстовое ядро AFNT320);
- кнопка (normal/pressed/disabled/focused);
- окно по списку объектов (`win_draw`, `win_draw_item`, `win_update`),
  модальные `win_open`/`win_close` с backstore;
- цикл событий `win_poll`/`win_track` (мышь + клавиатура + горячие клавиши).

Post-MVP ABI 1.0: поле ввода `win_edit`, фокус клавиатуры и
Tab-обход (§14.5), listbox, скроллбар, прогрессбар и иконки.
Совместимое расширение ABI 1.1 добавляет checkbox/radio button,
автоматическое изменение их состояния и `WIN_EV_CHANGE` (§16.5).
Перетаскивание бегунка не входит в ABI 1.0: кликов по стрелкам, страницам
и ползунку достаточно для несложного GUI; drag добавляется отдельным
entry только при подтверждённой необходимости.

Вне целей библиотеки (сознательное упрощение, не планируется и после 1.0):

- перекрывающиеся немодальные окна, z-order и clipping окон — оконная
  модель ограничена LIFO-стеком модальных окон поверх фона;
- перемещение окон мышью;
- собственный драйвер мыши: используется только BIOS Mouse API;
- runtime-загрузка других DLL (см. §4 — libman этого не поддерживает).

Не входит в первую версию:

- режим 640×256×16 (отдельная `WIN640.DLL`);
- вывод текста произвольным шрифтом, кроме поставляемого 8-пиксельного
  (шрифт заменяется внешним файлом без пересборки DLL, §3.6).

## 3. Аппаратная модель и окружение

### 3.1 Видеопамять и экраны

Доступ к экрану — как в GFX320/AFNT320: VRAM-страница `#50` подключается в
выбранное CPU-окно, `PORT_Y=#89` выбирает строку `0..255`, X — смещение от
базы буфера. Базы внутри строки:

```text
экран 0: WINDOW_BASE + #000
экран 1: WINDOW_BASE + #140
```

Библиотека пишет через алиас `#50` (запись с обновлением DRAM-зеркала, без
прозрачности); единственное исключение — keyed-иконки, использующие алиас
`#58` (прозрачность `#FF` с обновлением зеркала, §16.1). Алиасы
`VRAM_ONLY` (`#54`/`#5C`) не используются: сохранение фона под модальным
окном читает DRAM-зеркало, и оно обязано соответствовать экрану.

Целевой экран — глобальная настройка `win_set_screen(0|1)`. Все рисующие
функции используют текущее значение; отдельного per-call выбора экрана нет.
Переключение видимого экрана (DSS `SELPAGE #54` / `SETVMOD #50`) остаётся
обязанностью приложения; типовой сценарий gfxview — GUI на экране 0,
полноэкранный контент на экране 1.

### 3.2 Акселератор

Используются команды `FILL`, `SET_BUFFER`, `FILL_VERT`, `COPY`, `COPY_VERT`
(`LD C,C` / `LD D,D` / `LD E,E` / `LD L,L` / `LD A,A`) с обязательным
завершением каждой блочной процедуры `LD B,B` и восстановлением `PORT_Y=#C0`
перед возвратом. Полный контракт акселератора — семантика защёлкивания
источника `COPY` и атомарность DI-секций — принимается по
`gfx320/specs.md` §3.4 и §15 без изменений.

У акселератора **есть** логические функции `FN_ACC`. FPGA реализует четыре
варианта результата:

```text
COPY  XMD = MD
OR    XMD = MD OR  accelerator_RAM
XOR   XMD = MD XOR accelerator_RAM
AND   XMD = MD AND accelerator_RAM
```

Логическая функция выбирается не портом и не предварительным
`LD D,(HL)`. После загрузки исходного блока во внутреннюю RAM команда
`OR (HL)` / `XOR (HL)` / `AND (HL)` одновременно выбирает функцию и читает
блок назначения; непосредственно следующая `LD (HL),A` записывает
результат. Для XOR безопасная форма одной блочной процедуры:

```z80
        ld      l,l       ; COPY: включить работу с внутренней RAM
        ld      a,(de)    ; загрузить исходный блок
        xor     (hl)      ; destination XOR accelerator_RAM
        ld      (hl),a    ; записать весь результирующий блок
        ld      b,b       ; обязательное завершение
```

Размер блока задаётся заранее через `LD D,D`; вся последовательность
выполняется под `DI`, без вставок между `XOR (HL)` и `LD (HL),A`.
`win_invert_rect` использует именно этот аппаратный XOR (§9.1). OR/AND
аппаратно подтверждены, но отдельные публичные примитивы для них в ABI 1.0
не нужны.

Адреса источника и приёмника `COPY` — обычные логические адреса Z80,
проходящие через текущее страничное отображение. Поэтому каждой стороной
копирования может быть как обычная DRAM/EMM-страница, так и VRAM-алиас:

- чтение через VRAM-окно возвращает теневое DRAM-зеркало;
- запись в обычную EMM-страницу изменяет эту страницу;
- запись через `#50`/`#58` изменяет VRAM и её зеркало согласно семантике
  выбранного алиаса.

Следовательно, backstore (§13.3) копируется акселератором в обе стороны:
VRAM-shadow→EMM при сохранении и EMM→VRAM при восстановлении. Никакого
ограничения «обычная EMM-страница не может быть приёмником» нет.

### 3.3 Мышь

Только BIOS Mouse API (`RST #30`):

| C | Функция | Регистры |
|---:|---|---|
| 0 | INIT | — |
| 1 | SHOW CURSOR | — |
| 2 | HIDE CURSOR | — |
| 3 | READ STATE | out: `A`=кнопки (bit0 LMB, bit1 RMB, bit2 MMB), `HL`=X, `DE`=Y |
| 4 | GOTO | in: `HL`=X, `DE`=Y |
| 9 | LOAD CURSOR | in: `IX`=спрайт, `H`=высота, `L`=ширина, `D/E`=hot spot |

Инициализацию драйвера (`C=0` INIT) выполняет приложение, один раз, до
первого вызова `win_poll`/`win_track`; библиотека INIT не вызывает и
использует только READ STATE, SHOW/HIDE и LOAD CURSOR.

Отрисовку и восстановление фона под курсором выполняет драйвер BIOS.
Библиотека курсор не рисует. Если в `WinTrack.options` установлен
`WIN_TRK_SHOW_CUR`, она временно прячет его (`C=2`) на время собственных
перерисовок внутри `win_poll`/`win_track` и показывает обратно; без этого
флага предполагает, что курсор уже скрыт, и не меняет его состояние.
Приложение обязано прятать курсор перед прямыми вызовами рисующих entry
поверх области курсора и показывать после (или держать курсор скрытым на
время построения экрана).

Формат спрайта курсора — формат BIOS: байт на пиксель, `#00` чёрный,
`#FE` белый, `#FF` прозрачный. Встроенные курсоры: стрелка 13×9 (hot spot
0,0) и «ожидание» 14×9 (hot spot 7,4) — данные заимствуются из
`gfxview/gfx_ms.asm`.

BIOS-курсор работает на видимом экране. Библиотека не пытается определять,
совпадает ли видимый экран с целевым: при `WIN_TRK_SHOW_CUR` временный
HIDE/SHOW выполняется всегда. Это дешёвая и безопасная операция; без
дополнительного глобального состояния API остаётся однозначным.

### 3.4 Клавиатура

Только DSS `SCANKEY` (`C=#31`, `RST #10`): `ZF=1` — буфер пуст; иначе
`E`=ASCII, `D`=скан-код, `B`=модификаторы. Сырые порты клавиатуры не
читаются. «Сырой код» в терминах библиотеки — пара (ASCII, скан-код) плюс
байт модификаторов, как их возвращает DSS.

### 3.5 Требования к окружению вызова

- активен режим DSS `#81`; библиотека его не включает и не выключает;
- `win_init` успешно загрузил встроенный шрифт (§3.6); при отсутствии или
  повреждении хвоста сам `l_load` завершается ошибкой;
- maskable interrupts у приложения разрешены: `win_poll`/`win_track`
  используют BIOS/DSS-вызовы, а `WIN_TRK_HALT` — `HALT`; внутри собственных
  DI-секций рисования библиотека сама управляет прерываниями;
- NMI-источник отсутствует во время рисующих DI-секций (контракт
  `gfx320/specs.md` §15);
- палитра: верхние 16 индексов (`#F0..#FF`) заняты стандартными цветами EGA
  (§8); остальные 240 индексов библиотека не трогает.

Конфигурация источников прерываний остаётся за приложением, и библиотека её
не изменяет и не измеряет. Из этого следует ограничение на темп автоповтора
(§14.4): `HALT` пробуждается **любым** прерыванием, а на Sprinter кроме
кадрового INT (~50 Гц) независимыми источниками являются CTC и COVOX/CBL
(`INT_X = !DFF(GND, (SVIDEO.INTT & KEYS.int), …) or !CBL_INT`,
`manual/09_advanced/01_interrupts.md`). Приложение с активным
COVOX/CTC-плеером получает существенно более частые пробуждения.

Как и GFX320, release-сборка не вызывает `GETVMOD` из loader hook и не
проверяет видеорежим перед каждым примитивом: это добавило бы системный
вызов в горячий путь. Приложение включает `#81` до `l_load` и не меняет
режим до `l_free`. `WIN_ERR_VIDEO_MODE` предназначен для debug-обёрток и
будущих явных проверок на границе приложения.

### 3.6 Шрифт в отдельной странице

Сконвертированный шрифт (`font_accel.bin`) занимает 10 608 байт: 1 КБ
таблиц (ширины, смещения, битовые маски колонок) плюс 8 байт масок
`#00/#FF` на каждую из 1198 непустых колонок. Вместе с кодом контролов он
не помещается в 16-КБ образ L0 (лимит включает таблицу релокаций).
Альтернатива — хранить в DLL компактный 2304-байтный `font.bin` и
разворачивать маски колонок на лету — отвергнута: образ получается
13–14 КБ, впритык к лимиту без запаса на рост кода, а рендер замедляется.

Поэтому данные шрифта находятся не в загружаемом 16-КБ prefix, а в
**trailing payload** файла `WIN320.DLL`. Страницей владеет сама библиотека:

- `win_init` получает в `A` открытый DSS-handle DLL. Актуальный
  `sources/libman` перед вызовом entry 0 оставляет файловый указатель на
  первом байте trailing payload;
- `win_init` выделяет одну 16-КБ страницу через `GETMEM #3D`, получает её
  физический номер через `EMM_FN5 #C5`, читает и проверяет блок `WF32`;
- при любой ошибке выделенная память освобождается, `win_init` возвращает
  `CF=1` и код в `A`, поэтому весь `l_load` завершается ошибкой;
- во время вывода текста страница подключается во временное data-окно,
  выбранное политикой §18.2; отдельное временное окно занимает VRAM.
  Оба отображения существуют только внутри короткой DI-секции и полностью
  восстанавливаются перед разрешением прерываний;
- `win_free`, вызываемый менеджером из `l_free`, освобождает блок шрифта.

INIT вправе выполнять DSS/BIOS-вызовы, необходимые для чтения payload:
libman специально оставляет файл открытым до возврата entry 0 и закрывает
handle сразу после него. Вызывать из INIT сам libman по-прежнему нельзя.

Шрифтовой блок (генерируется инструментом из `font.bin`):

```text
offset size field
0      4    magic = "WF32"
4      1    format_version = 1
5      1    font_height = 8
6      2    data_size            ; размер данных, <= 16376
8      ...  данные font_accel.bin (таблицы + маски колонок)
```

Сборка дописывает блок в конец файла `WIN320.DLL`. Это безопасно для
libman: `l_load` читает и распаковывает только prefix, а файловый указатель
после него уже стоит на payload. Контрольная сумма prefix хвост не
покрывает. Поэтому `WF32` идёт **непосредственно первым байтом payload**;
offset/trailer для его поиска не нужны. `make verify` обязан подтверждать
загрузку DLL с хвостом.

После успешного `l_load` текстовые entry готовы к работе без
дополнительного вызова. Свободный остаток страницы (~5.7 КБ) в ABI 1.0
не используется.

Кодировка шрифта — **CP866**: глиф выбирается непосредственно значением
байта строки, таблица содержит все 256 позиций. Это кодировка исходников
и ресурсов gfxview, из которого взят `font.bin`. Псевдографика:
`#10`/`#11` — стрелки вправо/влево, `#18..#1B` — стрелки
вверх/вниз/влево/вправо (используются кнопками скроллбара). Замена шрифта
на другую кодовую страницу выполняется подменой файла шрифта без
изменения кода.

`win_load_font(DE=path)` заменяет текущий шрифт блоком из отдельного файла.
Файл должен начинаться с `WF32`; полный файл DLL эта функция не принимает.
`path` — ASCIIZ длиной не больше 255 байт независимо от
`win_set_text_format`, потому что это путь DSS, а не строка интерфейса.

Замена атомарна: библиотека выделяет временную страницу, загружает и
проверяет magic, версию и `data_size`, а только затем меняет
`font_block/font_page` и освобождает прежний блок. При ошибке файла,
формата или памяти временный блок освобождается, старый шрифт остаётся
рабочим. Повторный вызов допустим и предназначен, например, для смены
локализации.

### 3.7 Рабочие CPU-окна

Библиотека не закрепляет VRAM, шрифт, backstore, страницы иконок или
paged-строк за конкретным окном адресного пространства. По умолчанию
`WIN_WORK_AUTO=#FF`: непосредственно перед микропроцедурой выбираются одно
или два окна из WIN0..WIN3, кроме окна кода DLL и окна текущего `SP`.

Рекомендуемая и тестируемая раскладка:

```text
WIN3       WIN320.DLL (параметр window при l_load)
WIN0..WIN2 код, данные и стек приложения
```

Она гарантирует, что после исключения окна DLL и одного окна стека
останутся два окна для одновременного mapping VRAM+font,
VRAM+backstore либо VRAM+icon. Само окно стека никогда не переключается.
WIN0 является обычным кандидатом: если он выбран, прерывания запрещены до
полного восстановления страницы; внутри mapping не выполняются `RST`,
BIOS/DSS-вызовы, а активный источник NMI не допускается.

`win_set_work_windows` позволяет вместо автоматики явно назначить data- и
VRAM-окна. Настройка влияет только на временный
mapping, не резервирует окна между вызовами и не меняет правила размещения
клиентских данных (§5.3). Текущий `SP` проверяется заново в каждой
рисующей функции, поскольку приложение вправе перемещать стек.

Загрузка DLL не в WIN3 поддерживается, но окно кода всё равно исключается
из параметров и рабочих окон. Кроме того, `SP` не должен находиться в
целевом окне DLL уже при входе в `l_call`: менеджеру требуется рабочий
стек до того, как управление получит библиотека.

## 4. Переиспользование AFNT320 и ограничения libman

### 4.1 Результат анализа libman

Единственный нормативный источник — актуальный
`sources/libman/libman/*`. Загрузка и вызов одной DLL из другой через
libman невозможны. Причины:

- libman — не сервис DSS, а модуль, прилинкованный в EXE; у DLL нет способа
  получить адреса `l_load`/`l_call` (нет таблицы импорта, релокация — только
  «+старший байт адреса»);
- `l_call` нереентерабелен: единственный набор глобальных ячеек
  (`lcstart`, `lcoldp`, `lc_fun`, `lcflag`) плюс самомодифицируемый код
  восстановления страницы; вложенный `l_call` навсегда оставляет окно
  внешнего вызова подменённым;
- вложенные вызовы явно числятся открытым вопросом в `sources/libman/TODO.md`.

Refcount по имени файла также отсутствует: повторный `l_load` той же DLL
создаёт вторую копию со вторым `init`.

### 4.2 Принятое решение: общее текстовое ядро на уровне исходников

Функционал вывода текста не дублируется бинарно между приложениями, но и не
вызывается из `AFNT320.DLL` в runtime. Вместо этого текстовое ядро AFNT320
(рендер пропорционального шрифта через акселератор: `text_out_320`,
`prepare_colors_320`, конвертированный шрифт `font_accel.bin`) выделяется в
общие исходные модули:

```text
common/textcore320.inc   ; рендер текста, параметризован состоянием владельца
common/fontlayout.inc    ; константы и формат таблиц шрифта без самих данных
```

Обе DLL включают `textcore320.inc` и `fontlayout.inc`; AFNT320 отдельно
включает сгенерированный `font_accel.bin`, а WIN320 читает те же таблицы
из своей шрифтовой страницы. Публичный ABI AFNT320 не меняется. Это
тот же приём, что принят в `gfx320/specs.md` §9.7 для общего кода
GFX320/GFX640. Дублируется только код рендера (~1–1.5 КБ); данные шрифта у
WIN320 в образ не входят (§3.6). Выигрыш — полная независимость от
нереентерабельного libman и отсутствие координации окон между двумя DLL.

Ядро параметризуется размещением шрифта build-time опцией: AFNT320 читает
таблицы и маски из собственного окна кода (как сейчас), WIN320 — из
шрифтовой страницы, подключённой во временное data-окно (§3.6, §3.7).

Требование к рефакторингу afnt320 (этап 0): вынести ядро без изменения
поведения, пересобрать `AFNT320.DLL`, прогнать его визуальный тест.

### 4.3 Требования к хосту

Приложение линкует `sources/libman/libman/libman.asm` либо эквивалентную
сборку из того же каталога. Другие копии libman не считаются частью
поддерживаемой конфигурации WIN320.

## 5. Общие требования к ABI

### 5.1 Типы и координаты

Типы — как в `gfx320/specs.md` §4.1: `u8`, `u16` little-endian. Все
структуры packed, little-endian. Поля `reserved` вызывающий обнуляет;
ненулевое значение даёт `WIN_ERR_ARGUMENT`. Отрицательных координат нет.

Все неописанные биты полей `flags` зарезервированы и должны быть равны
нулю; ненулевое значение возвращает `WIN_ERR_UNSUPPORTED`. Это позволяет
старой DLL явно отклонить новый режим, а не интерпретировать его иначе.

Каждый дескриптор рисуемого объекта начинается одинаковым 8-байтным
заголовком геометрии:

```text
offset size field
0      2    x        ; u16
2      2    y        ; u16, допустимые значения 0..255
4      2    width    ; u16, пиксели
6      2    height   ; u16, пиксели, допустимые значения 0..256
```

Единый заголовок — центральное соглашение библиотеки: hit-test читает
первые восемь байт любого контрола и не обязан знать его тип, а `win_update`
и прямой вызов работают с той же самой структурой, что стоит в списке
объектов окна. Поэтому геометрия объекта хранится ровно в одном месте.

Все четыре поля — u16, включая `y` и `height`. Байтовые `y`/`height`
отвергнуты: `height=255` не описывает полноэкранный объект (256 строк), а
спецзначение «0 = 256» конфликтует с правилом «нулевой размер — пустая
операция» (§9.1) — вычисленный в runtime ноль превращался бы из
безобидного no-op в молчаливую заливку во весь экран — и непрозрачно для
C/Pascal-клиентов. Симметричные u16-оси дают и практические выгоды: Y мыши
BIOS (16-битный `DE`) сравнивается без расширения, горизонтальные и
вертикальные варианты примитивов обслуживаются одной подпрограммой с
перестановкой ролей осей, заголовок общий с будущей WIN640. Цена — 2 байта
на дескриптор.

**Координаты `x`,`y` дескрипторов относительны текущему началу отсчёта**
(§9.3), которое по умолчанию равно `0,0`. Единственное исключение —
`WinWindow`: его `x`,`y` абсолютные, потому что окно само задаёт начало
отсчёта (§12.2). Разной семантики у одной структуры в зависимости от места
использования нет: дескриптор, стоящий в списке окна, и он же, переданный
прямым вызовом, рисуются одинаково.

Итоговая экранная координата = начало отсчёта + поле дескриптора;
допустимо `x+width <= 320` и `y+height <= 256`, иначе —
`WIN_ERR_ARGUMENT` без записи в экран. Все суммы проверяются вместе с
переносом: 16-битное переполнение никогда не может превратить ошибочную
область в допустимую.

### 5.2 Возврат ошибок

Контракт совпадает с GFX320 (`gfx320/specs.md` §4.2): результат в `A`,
`A=0` — успех, `CF` не является каналом ошибок библиотеки для entry `>=1`;
`win_init` (entry 0) возвращает `CF=1` при `A!=0` для libman.

Коды ошибок (диапазон `#20..#2F`, не пересекающийся с `GFX_ERR_*` `#10..#17`
и кодами менеджеров `#01..#0F`):

| Код | Имя | Значение |
|---:|---|---|
| `#20` | `WIN_ERR_ARGUMENT` | некорректный параметр/структура |
| `#21` | `WIN_ERR_VIDEO_MODE` | активен не режим `#81` |
| `#22` | `WIN_ERR_WINDOW` | не удалось выбрать рабочие окна без конфликта с DLL/`SP` |
| `#23` | `WIN_ERR_BACKSTORE` | backstore не задан или не хватает страниц |
| `#24` | `WIN_ERR_DEPTH` | переполнение/исчерпание стека окон |
| `#25` | `WIN_ERR_UNSUPPORTED` | функция/флаг не поддерживается |
| `#26` | `WIN_ERR_BUSY` | конфликт незавершённой операции |
| `#27` | `WIN_ERR_FONT` | шрифт не загружен / ошибка файла или формата шрифтового блока |
| `#28` | `WIN_ERR_MEMORY` | не удалось выделить внутреннюю EMM-страницу |

### 5.3 Ограничения `l_call`

Идентичны GFX320 (`gfx320/specs.md` §4.3): до entry гарантированно доходят
только `A`, `DE`, `IX`, `IY`; `HL`/`BC` заняты диспетчером; результат не
возвращается в `A`, кроме кода ошибки. Указатели на дескрипторы передаются
в `DE`.

Рекомендуемая раскладка — загрузить `WIN320.DLL` в **WIN3**, а код, стек и
обычные данные приложения разместить в WIN0..WIN2. Тогда любой дескриптор,
обычная строка, массив или буфер редактирования в WIN0..WIN2 является
допустимым параметром. Пиксели иконок и большие наборы строк рекомендуется
держать в отдельных физических EMM-страницах (§16.1, §16.4), не расходуя
дефицитное адресное пространство WIN0..WIN2. Библиотека не резервирует
WIN0 и не требует постоянного VRAM-окна.

Во время `l_call` страница DLL подключена в окно, указанное при `l_load`,
и вытесняет оттуда страницу приложения. Только это окно недоступно
клиентским данным на всём протяжении вызова. При рекомендуемой загрузке в
WIN3 ограничение естественно выполняется для всех данных в WIN0..WIN2.

Рабочие страницы подключаются лишь на время короткой микропроцедуры:

- верхний дескриптор, текущий `WinItem`, дескриптор контрола и необходимые
  изменяемые поля копируются во внутренний scratch **до** mapping;
- строка длиной до 255 байт предварительно копируется в `text_scratch`;
  listbox делает это отдельно для каждой рисуемой строки, при необходимости
  временно подключая указанную строкой физическую EMM-страницу;
- после восстановления страниц библиотека записывает изменённые поля
  обратно в структуру приложения;
- иконка читается акселератором прямо из физической EMM-страницы,
  определённой парой `page, slot`; адрес ячейки вычисляется за `O(1)`.

Поэтому массивы и косвенные данные могут находиться даже в окне, которое
затем временно используется под VRAM, font или backstore: библиотека
восстанавливает страницу между элементами/строками. Единственное
постоянное ограничение — данные не должны находиться в окне самой DLL.

Libman знает номер вытесненной страницы: `_L_CALL` читает page-port
целевого окна, сохраняет байт во внутреннем самомодифицируемом коде
восстановления, а после entry возвращает страницу. Но этот байт не
является публичным ABI и не передаётся DLL ни в одном регистре. После
mapping чтение page-port
показывает уже страницу DLL, поэтому библиотека штатно определить прежнюю
страницу не может. Если данные приложения попали в это окно, C/Pascal-
обёртка должна до `l_call` скопировать их в WIN0..WIN2. Даже переданный
номер сам по себе проблему не решает: повторное mapping старой страницы в
окно DLL немедленно скроет исполняемый код.

Рекомендуемые раскладки памяти для SDCC и Turbo Pascal — §21.

### 5.4 Реентерабельность и владение состоянием

Библиотека нереентерабельна. Запрещены вызовы WIN320 из ISR и повторный
вход во время незавершённой операции (в том числе из обработчика NMI).

Состояние трекинга мыши и клавиатуры (нажатый объект, фаза автоповтора,
последняя позиция курсора, наведённый объект) **принадлежит вызывающему** и
живёт в поле `state` его дескриптора `WinTrack` (§14.1). Два независимых
диалога с двумя `WinTrack` не мешают друг другу и не требуют ручного
сброса; «сброс» — это обнуление `state` приложением. Фокус клавиатуры
хранится в дескрипторе окна (`WinWindow.focus`), а не в библиотеке.

Глобальным состоянием DLL остаются только вещи, глобальные по существу:
целевой экран, предпочтения рабочих окон, шрифтовая страница, тема, формат
строк, начало отсчёта, backstore и стек модальных окон (§18.1).

### 5.5 Владение данными

Часть структур приложения библиотека изменяет; они обязаны находиться в
writable RAM. При рекомендуемой загрузке DLL в WIN3 это может быть любое
место в WIN0..WIN2:

| Структура | Библиотека пишет |
|---|---|
| `WinWindow` | `focus`, `last_focus` |
| `WinItem[]` | `flags` (снятие `WIN_IT_DIRTY`) |
| `WinButton` | `flags` (`WIN_BTN_PRESSED`, `WIN_BTN_FOCUS`) |
| `WinEdit` | `flags`, `len`, `cursor`, `scroll` и сам буфер |
| `WinListbox` | `flags` (`WIN_LB_FOCUS`), `last_first`, `last_cursor` |
| `WinScrollbar` | `thumb_pos`, `thumb_len`, `last_pos` |
| `WinProgress` | `last_px` |
| `WinChoice` | `flags` (`WIN_CH_CHECKED`, производный `WIN_CH_FOCUS`) |
| `WinTrack` | выходные поля, `state` |

Только читаются: `WinRect`, `WinLabel`, `WinIcon`, `WinTheme`,
`WinKey[]`, `WinCursor`, строки, таблица ссылок `items`
listbox и пиксели иконок. Их допустимо размещать в константных сегментах;
страницы изображений и paged-строк принадлежат приложению и библиотекой
не освобождаются.
Следствие для биндингов: в C нельзя объявлять `WinWindow`, `WinItem[]` и
изменяемые контролы как `const`; в Turbo Pascal typed const допустимы
(они записываемы).

| Функция | Вход | Результат при `A=0` |
|---|---|---|

| `win_free` | нет; только из `l_free` | `A=0` |
| `win_set_work_windows` | `D=data window`, `E=VRAM window`; каждое `0..3` или `WIN_WORK_AUTO=#FF` | `A=0` |
| `win_set_screen` | `E=0/1` | `A=0` |
| `win_get_version` | нет | `D=ABI major` (=1), `E=ABI minor` (=1), `IX=capabilities` |
| `win_get_config` | `DE=&WinConfig` | заполненная структура |

| `win_set_theme` | `DE=&WinTheme` или `DE=0` (тема по умолчанию) | `A=0` |
| `win_set_text_format` | `E=0 ASCIIZ / 1 length-prefixed` | `A=0` |

| `win_draw_item` | `DE=&WinWindow`, `IX=index` | `A=0` |
| `win_update` | `DE=&WinWindow` | `A=0`, `E`=число перерисованных объектов |

Для `win_set_work_windows` значения `D` и `E`, отличные от `#FF`, должны
задавать разные окна и не совпадать с окном DLL. Это закрепление роли
только на время mapping, а не постоянно занятые окна. `WIN_WORK_AUTO`
выбирает роль автоматически;
это значение по умолчанию для обеих ролей и рекомендуемый режим. Явная
настройка, совпавшая с окном актуального `SP`, даёт `WIN_ERR_WINDOW` в
рисующей функции без изменения экрана. Операции, которым нужна только
VRAM, data-настройку не используют.

Все публичные функции сохраняют регистры, не объявленные входом или
результатом. Отдельных `_fast`/`_clip` ярусов нет: контролы — не горячие
игровые пути. Одиночные рисующие entry сначала проверяют свой дескриптор
и при ошибке ничего не рисуют. Агрегатные `win_draw`/`win_update`
используют последовательную семантику без дорогого второго прохода:
успешно обработанные предыдущие объекты уже нарисованы, обработка
останавливается на ошибочном, его и последующие dirty-флаги не снимаются.
`win_open` остаётся атомарным благодаря восстановлению backstore (§13.2).

`WinConfig` (по образцу `GfxConfig`, с протоколом `struct_size`
`gfx320/specs.md` §4.6):

```text
offset size field
0      1    struct_size          ; вход: ёмкость; выход: полный размер = 20
1      1    required_dss_mode = #81
2      2    width = 320
4      2    height = 256
6      1    vram_window          ; 0..3 либо #FF AUTO
7      1    code_window
8      1    screen               ; текущий целевой экран 0/1
9      1    backstore_pages      ; сколько страниц передано
10     1    backstore_depth      ; текущая глубина стека окон (макс. 4)
11     1    font_height = 8
12     2    capabilities
14     1    font_page            ; informational; #FF = нет, клиент не освобождает
15     1    data_window          ; 0..3 либо #FF AUTO
16     2    origin_x             ; текущее начало отсчёта (§9.3)
18     1    origin_y
19     1    text_format          ; 0 ASCIIZ, 1 length-prefixed
```

Вызывающий задаёт `struct_size>=1`; библиотека записывает не больше
указанной ёмкости и всегда заменяет первый байт полным известным ей
размером. Так старый клиент может безопасно работать с новой расширенной
структурой, а новый — определить, какие хвостовые поля доступны у старой
DLL. Поля `data_window`/`vram_window` возвращают настройки, а не
мгновенный результат AUTO-выбора: вне микропроцедуры активных рабочих окон
нет, исходный mapping уже восстановлен.

`capabilities`:

```text
bit 0  WIN_CAP_CORE        ; примитивы, окна, poll/track
bit 1  WIN_CAP_EDIT
bit 2  WIN_CAP_LISTBOX
bit 3  WIN_CAP_SCROLLBAR
bit 4  WIN_CAP_PROGRESS
bit 5  WIN_CAP_ICON
bit 6  WIN_CAP_FOCUS       ; Tab-обход фокуса (§14.5)
bit 7  WIN_CAP_PASCAL_STR  ; поддержан формат строк с байтом длины
bit 8  WIN_CAP_CHECKBOX
bit 9  WIN_CAP_RADIOBUTTON
bits 10..15 reserved = 0
```

`win_get_version` возвращает версию ABI, а не номер конкретной сборки.
Версия этой спецификации — 1.1; новые совместимые entry повышают minor,
изменение существующей структуры или семантики требует нового major.

## 8. Цвет, палитра, тема

### 8.1 Две разные вещи: `color` и `attr`

В первой редакции спецификации оба понятия были слиты в один байт `attr`, и
это давало противоречие: рамке нужны два цвета (свет и тень) в двух
нибблах, а панели — рамка **и** цвет тела, для которого нибблов уже не
оставалось. Модель разделена:

- **`color`** — один индекс `0..15`. Им пользуются геометрические примитивы:
  цвет заливки, цвет тела панели, цвет линии.
- **`attr`** — байт `d7..d4` background, `d3..d0` foreground. Им пользуется
  **только текст**.
- **роли** (свет/тень/тело/текст/выделение/…) живут в таблице темы и в
  дескрипторах не хранятся вовсе.

Значение `#FF` в любом поле `color` или `attr` означает «взять из темы».
Это значение по умолчанию для всех дескрипторов, поэтому типичный
интерфейс не содержит явных цветов и перекрашивается одним
`win_set_theme`. Сам вызов тему только заменяет и экран не трогает:
открытый интерфейс перекрашивается последующим полным `win_draw`.

Библиотека отображает индексы `0..15` в верхние 16 позиций палитры:
реальный индекс пикселя = `#F0 | color`. Это соглашение gfxview и AFNT320;
нижние 240 индексов остаются приложению.

Стандартные цвета (палитра EGA, как в `gfxview/gfx_pal.asm`):

```text
0  (#F0) чёрный          7  (#F7) тёмно-серый 808080
1  (#F1) синий           8  (#F8) светло-серый C0C0C0
                        15  (#FF) белый
```

### 8.2 `WinTheme` (16 байт)

`win_set_theme(DE=&WinTheme)`; `DE=0` восстанавливает тему по умолчанию.
Каждый байт — индекс цвета `0..15`, кроме `focus_mask`.

```text
offset  имя                    по умолчанию
0       WIN_TH_LIGHT           15   свет бевеля
1       WIN_TH_SHADOW          7    тень бевеля
2       WIN_TH_FACE            8    тело панелей, кнопок, окон
3       WIN_TH_DESKTOP         1    фон рабочего стола
4       WIN_TH_TEXT            0    текст на теле
5       WIN_TH_TEXT_DISABLED   7    текст выключенного контрола
6       WIN_TH_FIELD_BG        15   фон поля ввода и списка
7       WIN_TH_FIELD_FG        0    текст в поле ввода и списке
8       WIN_TH_CURSOR_BG       1    фон выделенной строки/курсора
9       WIN_TH_CURSOR_FG       15   текст выделенной строки/курсора
10      WIN_TH_PROGRESS        7    фон полосы прогресса
11      WIN_TH_PROGRESS_FILL   1    заполненная часть полосы
12      WIN_TH_SCROLL_TRACK    7    трек скроллбара
13      WIN_TH_SCROLL_THUMB    1    совместимость ABI; ползунок использует FACE
14      WIN_TH_FOCUS_MASK      #0F  XOR-маска пунктира фокуса (полный байт)
15      reserved = 0
```

Набор ролей и их имена согласованы с `ui_lib/include/ui_defs.inc`
(`UI_THEME_*`), чтобы приложения, портируемые между текстовым и
графическим интерфейсом, использовали одни и те же понятия.
Таблица копируется во внутреннее состояние DLL; после возврата указатель
клиенту больше не нужен.

### 8.3 `win_style`

`win_style(E=flags, D=desktop_color)`:

```text
bit 0  WIN_STYLE_PALETTE   ; загрузить 16 EGA-цветов в #F0..#FF текущего экрана
bit 1  WIN_STYLE_CLEAR     ; залить текущий экран цветом D (0..15; #FF = WIN_TH_DESKTOP)
bit 2  WIN_STYLE_BOTH      ; применить к обоим экранам
```

Палитра загружается прямой записью в палитровые регистры VRAM-строки
(`gfx320/specs.md` §3.5), без per-color BIOS-вызовов. `win_style` не
обязателен: приложение может настроить палитру само (например, через
GFX320 или BIOS).

## 9. Примитивы, строки, начало отсчёта

### 9.1 `WinRect` (10 байт)

Один дескриптор на пять entry: заливка, рамка, панель, разделитель,
инверсия/фокус. Он же описывает невидимую зону в списке объектов окна.

```text
offset size field
0      2    x
2      2    y
4      2    width
6      2    height
8      1    color       ; см. таблицу ниже; #FF = из темы
9      1    flags
```

`flags`:

```text
bit 0  WIN_RC_SUNKEN     ; 0 = raised (выпуклый), 1 = sunken (утопленный)
bit 1  WIN_RC_VERTICAL   ; только win_separator: 0 = горизонтальный
```

Смысл `color` по entry:

| Entry | `color` | `#FF` означает |
|---|---|---|
| `win_fill_rect` | цвет заливки | `WIN_TH_FACE` |
| `win_panel` | цвет тела панели | `WIN_TH_FACE` |
| `win_frame` | не используется | — |
| `win_separator` | не используется | — |
| `win_invert_rect` | полная XOR-маска | `WIN_TH_FOCUS_MASK` |
| `win_focus_rect` | полная XOR-маска | `WIN_TH_FOCUS_MASK` |

Свет и тень бевеля у `win_frame`, `win_panel` и `win_separator` всегда
берутся из темы (`WIN_TH_LIGHT`/`WIN_TH_SHADOW`) и меняются местами при
`WIN_RC_SUNKEN`.

Описание entry:

- `win_fill_rect` — заливка прямоугольника (акселератор: `FILL_VERT` по
  колонкам или `FILL` по строкам — выбор по геометрии, как в
  `gfx_fill_rect`).
- `win_frame` — рамка толщиной 1 пиксель без заливки тела: raised —
  верх/лево цветом `WIN_TH_LIGHT`, низ/право `WIN_TH_SHADOW`; sunken —
  наоборот.
- `win_panel` — `win_frame` + заливка внутренности цветом `color`. Базовый
  строительный блок окна.
- `win_separator` — 3D-линия толщиной 2 пикселя: горизонтальная (строка
  `WIN_TH_SHADOW` + строка `WIN_TH_LIGHT`) или вертикальная при
  `WIN_RC_VERTICAL`. Общая геометрия остаётся правдивой: для
  горизонтального разделителя требуется `height=2`, для вертикального —
  `width=2`; вторая размерность задаёт длину линии.
- `win_invert_rect` — XOR каждого байта области с маской `color`.
  Выполняется аппаратным `FN_ACC=XOR` через обычный алиас `#50`, поэтому
  DRAM-зеркало остаётся синхронным. Библиотека один раз заполняет
  `text_scratch` повторяющейся маской, загружает блок во внутреннюю RAM
  акселератора и применяет его к строкам прямоугольника; ширина 257..320
  делится на чанки не больше 256 байт. Для очень коротких участков
  допускается CPU-путь, если измеренный порог делает его быстрее.
  Используется для выделения и пользовательской hover-подсветки.
- `win_focus_rect` — пунктирный прямоугольник-индикатор фокуса по границам
  области: XOR маской `color` через каждый второй пиксель, фаза пунктира
  привязана к чётности абсолютных координат. Операция самообратима:
  повторный вызов с теми же параметрами полностью восстанавливает фон,
  поэтому индикатор снимается без перерисовки контрола. Библиотека не
  применяет XOR к произвольным объектам автоматически (§14.5);
  примитив предназначен для императивного интерфейса и пользовательских
  контролов.

Пустые размеры (`width=0` или `height=0`) — успешная пустая операция.
Для непустых `win_frame`, `win_panel` и `win_focus_rect` требуются
`width>=2,height>=2`; иначе нет однозначной пары противоположных граней.
У separator толщина ровно 2 px, как указано выше. Выход за экран —
`WIN_ERR_ARGUMENT` без записи.

### 9.2 Формат строк

`win_set_text_format(E)` задаёт, как библиотека читает **все** строки
интерфейса (лейблы, тексты кнопок, элементы listbox, буфер `win_edit`):

```text
0  WIN_TXT_ASCIIZ    ; указатель на строку, терминатор #00 (C, ассемблер)
1  WIN_TXT_PASCAL    ; указатель на байт длины, далее байты строки (Turbo Pascal)
```

Настройка глобальная и по умолчанию `WIN_TXT_ASCIIZ`. Приложение пишется на
одном языке, поэтому per-control переключение в ABI 1.0 не вводится;
внутри библиотеки формат разбирается в одном месте — функции выборки
строки, поэтому его цена — один бит состояния и одна ветвь, а не два
дополнительных байта в каждой структуре.

Длина любой статической строки интерфейса ограничена 255 байтами.
В режиме `WIN_TXT_ASCIIZ` библиотека ищет `#00` не дальше 255-го байта и
возвращает `WIN_ERR_ARGUMENT`, если терминатора нет; в Pascal-режиме длина
уже задана первым байтом. Ограничение предотвращает неограниченное чтение
памяти при ошибочном указателе и достаточно для экрана шириной 320 px.

`win_edit` в режиме `WIN_TXT_PASCAL` поддерживает длину в нулевом байте
буфера, что делает буфер напрямую совместимым с `string[maxlen]` TPC.

Кодировка байтов — CP866 (§3.6).

### 9.3 Начало отсчёта

Все координаты дескрипторов относительны текущему началу отсчёта:

```text
абсолютный x = origin_x + descriptor.x
абсолютный y = origin_y + descriptor.y
```

- после `win_init` начало отсчёта равно `0,0` — приложение, не
  использующее окна, работает в абсолютных экранных координатах и ничего
  про этот механизм знать не обязано;
- `win_draw`, `win_draw_item`, `win_update`, `win_poll`, `win_track`
  устанавливают начало отсчёта из полей `x,y` переданного `WinWindow` на
  время работы и восстанавливают прежнее на выходе — эти пути
  контекстно-независимы и не зависят от глобальной настройки;
- `win_open` устанавливает начало отсчёта в координаты открытого окна и
  запоминает прежнее; `win_close` возвращает его. Поэтому точечное
  обновление контрола прямым вызовом внутри открытого модального окна
  работает без дополнительных действий;
- `win_set_origin` задаёт начало отсчёта явно — например, чтобы дорисовать
  что-то на рабочем столе при открытом диалоге.

Следствие: диалог перемещается изменением двух полей `WinWindow.x/y` —
никакие координаты объектов пересчитывать не нужно. Это то же соглашение,
что принято в `ui_lib` («descriptors … must remain relocatable»).

## 10. Текст: `win_label`

Рендер — общее текстовое ядро AFNT320 (§4.2): пропорциональный шрифт,
глифы 8 пикселей высотой, продвижение 1..8 пикселей, фон символа
закрашивается ядром. Данные шрифта читаются из шрифтовой страницы,
подключаемой во временное data-окно внутри DI-секций (§3.7, §18.2); без
загруженного шрифта — `WIN_ERR_FONT`. В 320×256 при типовой ширине 6 px
помещается ~53 символа в строке.

`WinLabel` (12 байт):

```text
offset size field
0      2    x
2      2    y
4      2    width       ; поле в пикселях; 0 = не ограничивать
6      2    height      ; высота поля, обычно 8; участвует в FILL и hit-test
8      1    attr        ; bg:fg; #FF = WIN_TH_TEXT на WIN_TH_FACE
9      1    flags
10     2    text
```

`flags`:

```text
bits 0..1  выравнивание: 0 left, 1 center, 2 right
bit 2      WIN_LABEL_FILL   ; предварительно залить поле width×height фоном attr
bit 3      WIN_LABEL_CLIP   ; обрезать текст по width с заменой хвоста на «..»
                            ; (приём prtDirName из gfxview)
```

При `width=0` допускается только выравнивание left, флаги FILL/CLIP
игнорируются. Ширина строки в пикселях считается по таблице продвижений
шрифта; глиф, пересекающий правую границу экрана, обрезается ядром,
дальнейшие — не выводятся. Строка `text` может находиться в любом окне
приложения WIN0..WIN2 при рекомендуемой загрузке DLL в WIN3: до mapping
font+VRAM она копируется во внутренний `text_scratch` (§5.3).

`width=0` предназначен только для прямого декоративного вывода. Для
`WinLabel`, включённого в `WinWindow`, требуется ненулевая геометрия; для
динамически обновляемого label обязателен `WIN_LABEL_FILL`, чтобы более
короткий новый текст полностью стирал предыдущий.

## 11. Кнопка: `win_button`

`WinButton` (12 байт):

```text
offset size field
0      2    x
2      2    y
4      2    width
6      2    height
8      1    attr        ; текст: bg = тело, fg = надпись; #FF = из темы
9      1    flags
10     2    text        ; строка (или один символ при GLYPH)
```

`flags`:

```text
bit 0  WIN_BTN_GLYPH     ; text — один символ псевдографики
bit 1  WIN_BTN_FOCUS     ; рисовать индикатор фокуса; в декларативном пути
                         ; поддерживается библиотекой из WinWindow.focus (§14.5)
bit 2  WIN_BTN_PRESSED   ; нажатое состояние
bit 3  WIN_BTN_DISABLED  ; выключено
```

Отрисовка: панель телом (`attr` bg или `WIN_TH_FACE`), рамка raised или
sunken при `WIN_BTN_PRESSED`; текст центрируется по обеим осям, при
нажатии смещается на +1,+1. Disabled: текст цветом `WIN_TH_TEXT_DISABLED`,
нажатие не анимируется. При `WIN_BTN_FOCUS` дополнительно рисуется
пунктирный прямоугольник внутри рамки с отступом 2 px (§14.5).

Анимацию нажатия по мыши выполняет `win_poll`/`win_track` (§14),
устанавливая и снимая `WIN_BTN_PRESSED` и перерисовывая кнопку её же
функцией. Объект списка с флагом `WIN_IT_DISABLED` рисуется как disabled
независимо от `WIN_BTN_DISABLED`.

## 12. Окно и список объектов

### 12.1 Общая модель

Окно (оно же «вид» — область с собственным началом отсчёта) описывается
структурой `WinWindow` и **одним** массивом записей `WinItem`
фиксированного размера. Этот массив используется и для отрисовки, и для
hit-test, и для Tab-обхода, и для инкрементального обновления. Отдельной
таблицы зон мыши нет: зона объекта — это его собственная геометрия.

Запись `WinItem` не дублирует ни координаты, ни состояние контрола: она
содержит только тип, поведение зоны, идентификатор и указатель на
дескриптор. Поэтому перемещение кнопки — правка двух полей в `WinButton`,
и больше нигде.

Невизуальная зона (область экрана, которую приложение рисует само)
описывается записью типа `WIN_T_ZONE` с дескриптором `WinRect`: он даёт
геометрию, но не рисуется.

### 12.2 `WinWindow` (16 байт)

```text
offset size field
0      2    x           ; абсолютная экранная координата окна = начало отсчёта
2      2    y
4      2    width
6      2    height
8      1    color       ; тело окна; #FF = WIN_TH_FACE
9      1    flags
10     1    count       ; число записей в items, 0..255
11     1    focus       ; индекс записи с фокусом клавиатуры; #FF = нет
12     2    items       ; указатель на массив WinItem[count]
14     1    last_focus  ; internal: ранее нарисованный focus; #FF до первого draw
15     1    reserved = 0
```

Заголовок геометрии совпадает с общим (§5.1), но `x,y` окна — **абсолютные**
экранные координаты: окно и есть то, что задаёт начало отсчёта.

`flags`:

```text
bit 0  WIN_WND_NOPANEL   ; не рисовать тело окна, только объекты
bit 1  WIN_WND_SUNKEN    ; тело окна утопленное вместо выпуклого
```

Полноэкранный «рабочий стол» с зонами — это `WinWindow` c
`x=0,y=0,width=320,height=256` и `WIN_WND_NOPANEL`.

При `count=0` указатель `items` может быть 0 и `focus` обязан быть `#FF`.
При ненулевом `count` указатель обязателен; `focus` равен `#FF` либо
указывает на существующую запись с `WIN_IT_FOCUSABLE`, не hidden и не
disabled. Перед первым `win_draw` приложение ставит `last_focus=#FF`;
дальше поле принадлежит библиотеке.

По границам окна библиотека объекты не клиппирует (клиппинг — вне целей,
§2). Для обычного `win_draw` визуальный объект может выходить за границу
окна, если остаётся внутри экрана. Для `win_open` правило строже:
`width`/`height` окна должны быть ненулевыми, а каждый видимый рисуемый
объект обязан целиком лежать внутри его прямоугольника. Иначе
`WIN_ERR_ARGUMENT` возвращается до сохранения фона — `win_close` никогда
не оставляет невосстановленные пиксели. Для `WIN_T_LABEL` проверяется
фактическая область текста после измерения, clipping и выравнивания, а не
только объявленное поле `width×height`. Невидимые `WIN_T_ZONE` могут
выходить за границы окна, но не за экран.

### 12.3 `WinItem` (8 байт)

```text
offset size field
0      1    type        ; WIN_T_*
1      1    flags       ; WIN_IT_*
2      1    id          ; идентификатор события; #FF = событий нет
3      1    reserved = 0
4      2    control     ; указатель на дескриптор по типу
6      2    user_data   ; возвращается в событии
```

Терминатора нет: длину задаёт `WinWindow.count`. Фиксированный размер
записи даёт индексацию за `O(1)` (`items + index*8`), естественные массивы
в C и Pascal и отсутствие поиска терминатора. `id` выбирает приложение;
у интерактивных записей он должен быть `0..254`. `#FF` разрешён
декоративным записям, не имеющим `WIN_IT_HIT`, `WIN_IT_FOCUSABLE` и
`WIN_IT_HOVER`, и также используется событиями «вне объектов» (§14.4).
Уникальность id библиотека не проверяет: повтор id допустим,
если несколько объектов намеренно обрабатываются одной командой.

| `type` | Имя | `control` | Рисуется |
|---:|---|---|---|
| 0 | `WIN_T_NONE` | 0 | нет |
| 1 | `WIN_T_LABEL` | `&WinLabel` | да |
| 2 | `WIN_T_FILL` | `&WinRect` | да |
| 3 | `WIN_T_FRAME` | `&WinRect` | да |
| 4 | `WIN_T_PANEL` | `&WinRect` | да |
| 5 | `WIN_T_SEPARATOR` | `&WinRect` | да |
| 6 | `WIN_T_BUTTON` | `&WinButton` | да |
| 7 | `WIN_T_ICON` | `&WinIcon` | да |
| 8 | `WIN_T_PROGRESS` | `&WinProgress` | да |
| 9 | `WIN_T_SCROLLBAR` | `&WinScrollbar` | да |
| 10 | `WIN_T_LISTBOX` | `&WinListbox` | да |
| 11 | `WIN_T_EDIT` | `&WinEdit` | да |
| 12 | `WIN_T_ZONE` | `&WinRect` | нет |
| 13 | `WIN_T_CHECKBOX` | `&WinChoice` | да |
| 14 | `WIN_T_RADIOBUTTON` | `&WinChoice` | да |

`WIN_T_NONE` позволяет держать «дырку» в массиве без его пересборки.
Для него `control=0`, а интерактивные флаги запрещены. Для остальных
типов `control` обязан быть ненулевым.

`flags`:

```text
bit 0  WIN_IT_DIRTY      ; перерисовать при win_update; библиотека его снимает
bit 1  WIN_IT_HIDDEN     ; не рисовать и не тестировать
bit 2  WIN_IT_DISABLED   ; выключен; из hit-test и Tab исключён
bit 3  WIN_IT_HIT        ; объект участвует в hit-test мыши
bit 4  WIN_IT_FOCUSABLE  ; участвует в Tab-обходе фокуса (§14.5)
bit 5  WIN_IT_PRESS      ; анимировать нажатие (кнопка, стрелки скроллбара)
bit 6  WIN_IT_REPEAT     ; автоповтор, пока LMB удерживается над объектом
bit 7  WIN_IT_HOVER      ; события WIN_EV_HOVER / WIN_EV_LEAVE
```

Участие в hit-test задаётся положительным флагом `WIN_IT_HIT`, а не
выводится из типа: интерактивным объектам (кнопка, checkbox/radio, listbox, edit,
скроллбар, зона) приложение устанавливает его явно, декоративным — нет;
кликабельный лейбл или иконка-кнопка получаются тем же флагом без
специальных правил. Типовых умолчаний с отрицательным флагом-исключением
(«всё активно, кроме…») в ABI нет — одно правило вместо таблицы
исключений.

Для записи с `WIN_IT_HIT` общая геометрия обязана быть ненулевой и точно
совпадать с интерактивной областью. Поэтому label с `width=0` не может
быть hit-объектом, а separator использует явную толщину 2 px (§9.1).

`WIN_IT_DISABLED` всегда отключает ввод. Встроенное disabled-оформление
имеют button, checkbox/radio и текстовые интерактивные контролы; декоративные типы и
`WIN_T_ZONE` визуально не меняются. Это не требует специальных
disabled-версий иконок или геометрических примитивов.

`WIN_IT_PRESS`, `WIN_IT_REPEAT` и `WIN_IT_HOVER` допустимы только вместе
с `WIN_IT_HIT`: без hit-test они не имеют определённой области. Остальные
биты `reserved` обязаны быть нулевыми.

### 12.4 Отрисовка и инкрементальное обновление

- `win_draw(DE=&WinWindow)` — **полный рендер**: рисует тело окна (если нет
  `WIN_WND_NOPANEL`), затем объекты по возрастанию индекса, игнорируя
  `internal`-поля `last_*` и записывая в них актуальные значения;
  синхронизирует флаги фокуса из `WinWindow.focus`, записывает его в
  `last_focus` (§14.5). После успешной отрисовки каждой записи снимает у
  неё `WIN_IT_DIRTY`; при успехе флаг снят у всех записей. Ничего не
  сохраняет, вызывается повторно сколько угодно раз.
- `win_draw_item(DE=&WinWindow, IX=index)` — полный рендер одного объекта
  за `O(1)`; синхронизирует производный focus-флаг только этого объекта,
  тело окна не трогает. Для программной смены фокуса используется
  `win_update`, а не одиночный `win_draw_item`.
- `win_update(DE=&WinWindow)` — **дифференциальный** проход: для записей с
  установленным `WIN_IT_DIRTY` вызывает отрисовку контрола, которая
  использует `last_*` и перерисовывает только разницу; после успешной
  отрисовки записи снимает её флаг. Возвращает в `E` число
  перерисованных объектов. Если `focus !=
  last_focus`, библиотека дополнительно обновляет прежний и новый
  focus-объекты и затем записывает `last_focus=focus`; приложению не нужно
  вручную ставить им `WIN_IT_DIRTY`. Это штатный способ обновления после
  обработки события. Один индекс обрабатывается не более одного раза:
  dirty-состояние и смена фокуса объединяются в том же проходе, а `E`
  считает уникально перерисованные записи.
- прямой вызов (`win_button`, `win_listbox_draw`, …) — тот же дескриптор,
  без участия окна; координаты берутся относительно текущего начала
  отсчёта (§9.3). Отрисовка дифференциальная по `last_*` контрола; полная —
  когда `last_*` содержит sentinel `#FFFF` (после `*_init` или выставлен
  приложением).

Порядок отрисовки — по возрастанию индекса, поэтому объект с бо́льшим
индексом ложится поверх. Порядок hit-test — **обратный**, по убыванию
индекса: побеждает тот, кто нарисован последним (§14.4).

До отрисовки агрегат проверяет сам `WinWindow`: размеры, `count/items`,
`focus` и доступность массива. Ошибка в заголовке окна не меняет экран.
Дескрипторы отдельных объектов проверяются непосредственно перед их
отрисовкой, сохраняя лёгкую последовательную семантику §7.

`win_update` — лёгкий item-update, а не скрытый compositor. Ради скорости
он не хранит старую геометрию и не строит dirty-region:

- между полными `win_draw` нельзя менять геометрию, порядок и
  `WIN_IT_HIDDEN`; move/hide/show и смена темы требуют полного рендера;
- обновляемый контрол обязан восстановить все пиксели, которые мог
  изменить (кнопки и stateful-контролы делают это сами, динамический label
  использует `WIN_LABEL_FILL`);
- если изменяемый объект пересекается с объектами большего индекса,
  приложение также помечает эти верхние объекты dirty. `win_update`
  проходит их в порядке рисования и восстанавливает правильный z-order;
- `WIN_WND_NOPANEL` не предоставляет фон для стирания произвольных
  пользовательских объектов; его зоны обновляет само приложение.

Эти ограничения сохраняют предсказуемый `O(count)` проход и не превращают
библиотеку простого GUI в оконный compositor.

## 13. Backstore и модальные окна

### 13.1 Страницы backstore

`win_set_backstore(DE=&page_list, IX=count)` передаёт библиотеке список из
1..4 физических номеров 16-КБ страниц DSS. Приложение получает их цепочкой
`DSS GETMEM #3D` → `BIOS EMM_FN5 #C5` (как в `gfx320/specs.md` §11.4) и
освобождает после `win_free`. Страницы используются исключительно под
сохранённый фон окон. Страницы в списке должны быть различны и не должны
совпадать со шрифтовой страницей; нарушение — `WIN_ERR_ARGUMENT`.
Повторный `win_set_backstore` разрешён только при пустом стеке окон,
иначе — `WIN_ERR_BUSY`; успешный вызов копирует номера страниц во
внутреннее состояние и сбрасывает вершину аллокатора. Сам массив
`page_list` после возврата хранить не требуется.

### 13.2 `win_open` / `win_close`

`win_open(DE=&WinWindow)`:

1. проверяет ненулевой размер окна, его границы и границы всех визуальных
   объектов (§12.2), наличие backstore (иначе `WIN_ERR_BACKSTORE`),
   глубину стека окон (макс. 4, иначе `WIN_ERR_DEPTH`) и — точным расчётом
   аллокатора §13.3 — что фон окна помещается в оставшееся место страниц
   (иначе `WIN_ERR_BACKSTORE`); все проверки выполняются **до** каких-либо
   изменений экрана и состояния;
2. **всегда** копирует прямоугольник окна из DRAM-зеркала текущего экрана в
   backstore-страницы;
3. запоминает прежнее начало отсчёта и устанавливает своё;
4. вызывает `win_draw`.

Окно, фон под которым сохранять не нужно, рисуется через `win_draw` и не
попадает в стек — отдельного флага «без сохранения» нет. Тем самым
`win_close` всегда имеет что восстанавливать, и неопределённого поведения
не остаётся.

Атомарность: если шаг 4 вернул ошибку (некорректный объект списка),
`win_open` восстанавливает только что сохранённый фон, возвращает начало
отсчёта, снимает запись со стека и возвращает код ошибки `win_draw` —
экран и состояние библиотеки остаются как до вызова; частично нарисованный
диалог на экране не остаётся.

`win_close` восстанавливает фон верхнего окна стека, снимает его со стека и
возвращает прежнее начало отсчёта. Порядок закрытия — строго LIFO; вызов
при пустом стеке — `WIN_ERR_DEPTH`.

Запись стека:

```text
x, y, width, height, screen, alloc_page, alloc_offset,
prev_origin_x, prev_origin_y
```

Это **внутренняя** запись DLL, а не структура, которую заполняет
пользователь. Поле `screen` автоматически получает текущее значение
`win_set_screen` в момент `win_open`. `win_close` берёт экран из верхней
записи и восстанавливает фон именно туда, независимо от текущей глобальной
настройки; саму настройку `win_set_screen` он не меняет.

Поэтому вложенные окна на разных экранах имеют однозначную LIFO-семантику.
Например, после `set_screen(0); open(A); set_screen(1); open(B)` первый
`close` восстанавливает `B` на экране 1, второй — `A` на экране 0, а
текущим целевым экраном после обоих вызовов остаётся 1. Приложение не
передаёт и не может подменить сохранённое поле `screen`.

### 13.3 Аллокатор и перенос строк

Место в backstore-страницах распределяет LIFO bump-аллокатор: вершина —
пара (`page_index`, `offset`); запись стека окон хранит вершину на момент
своего сохранения (`alloc_page`, `alloc_offset`), и `win_close`
откатывает вершину к ней. Здесь «страница» означает один 16-КБ физический
EMM-блок из массива `page_list`, ранее переданного
`win_set_backstore`; `page_index` — индекс в этом массиве, а не номер
экрана и не CPU-окно WIN0..WIN3. Правила размещения:

- строка окна (`width` байт, не более 320) **никогда не делится между
  страницами**: если до конца текущей страницы остаётся меньше `width`
  байт, остаток пропускается (padding), `page_index` увеличивается, а
  строка кладётся с offset 0 физической страницы
  `page_list[page_index]`;
- проверка ёмкости использует ту же операцию для каждой строки:
  `if offset+width>16384: page_index++, offset=0`, затем
  `offset+=width`. Если новый `page_index>=page_count`, `win_open`
  возвращает `WIN_ERR_BACKSTORE` до изменения экрана. Простая формула
  `16384 div width` применима только к пустой странице с offset 0 и не
  используется для вложенного окна при произвольной текущей вершине.

Перенос строки: backstore-страница подключается во временное data-окно,
VRAM-алиас `#50` — во временное VRAM-окно (§3.7). Строка хранится целиком
в одной странице и целиком переносится в одной DI/map/unmap-секции.
`WIN_BACKSTORE_CHUNK=256`: нулевой аппаратный счётчик означает 256 байт,
поэтому строка шириной до 256 использует одну команду `COPY`, а шириной
257..320 — две последовательные команды `256 + остаток` без
промежуточного переключения mapping. Каждая команда заканчивается
непосредственным `LD B,B`; после полной строки восстанавливаются
`PORT_Y=#C0`, обе страницы и исходное состояние прерываний.
Промежуточный буфер не нужен.

И сохранение (VRAM-shadow→EMM), и восстановление (EMM→VRAM) выполняются
горизонтальным акселераторным `COPY`. В обеих фазах адреса являются
обычными логическими адресами через текущий mapping (§3.2); приёмником
сохранения является обычная EMM-страница, а приёмником восстановления —
алиас `#50`.

Для backstore приоритетом Stage 2 является скорость полной строки, поэтому
ограничение `WIN_DI_BUDGET_US` к этой операции не применяется. Сохранение
и восстановление тестируются отдельно.

Перед каждым чанком выбираются два рабочих окна, не совпадающие с окном
DLL и окном текущего `SP`; сами эти окна могут быть любыми из WIN0..WIN3.
При рекомендуемой раскладке DLL→WIN3 это не ограничивает размещение
структур и данных приложения в WIN0..WIN2.

Так как источник — DRAM-зеркало, всё, что приложение нарисовало в
перекрываемой области через `VRAM_ONLY` (например, спрайты GFX320), в
сохранённый фон не попадает.

## 14. События: `win_poll` и `win_track`

### 14.1 Дескриптор `WinTrack` (32 байта)

```text
offset size field
0      2    window        ; &WinWindow: объекты + начало отсчёта; 0 = только клавиатура
2      2    keys          ; &WinKey[key_count]; 0 = нет
4      1    key_count
5      1    options
; --- выходные поля, заполняются перед возвратом ---
6      1    event         ; WIN_EV_*
7      1    id            ; WinItem.id или WinKey.id
8      1    index         ; индекс записи WinItem; #FF = событие не от объекта
9      1    part          ; подобласть контрола; 0 = не задана
10     2    mouse_x
12     1    mouse_y
13     1    buttons       ; состояние кнопок мыши на момент события
14     1    key_ascii
15     1    key_scan
16     1    key_mods
17     1    reserved = 0
18     2    item          ; listbox: абсолютный индекс строки; иначе 0
20     2    user_data     ; из сработавшего объекта
; --- настройка темпа автоповтора (0 = значение по умолчанию) ---
22     1    repeat_delay  ; итераций опроса до первого WIN_EV_REPEAT
23     1    repeat_rate   ; итераций между повторами
; --- внутреннее состояние трекинга, принадлежит вызывающему ---
24     8    state         ; обнуляется приложением перед первым вызовом
```

`state` — единственное место, где живёт состояние «какой объект нажат»,
«фаза автоповтора», «над каким объектом курсор», «прежние координаты и
кнопки». Библиотека своих копий не держит, поэтому два диалога с двумя
`WinTrack` полностью независимы, а «сброс» — это обнуление восьми байт
приложением. Содержимое `state` — internal, приложение его не
интерпретирует.

`options`:

```text
bit 0  WIN_TRK_ANY_KEY   ; возвращать любую клавишу (WIN_EV_KEY),
                         ; а не только совпавшие с таблицей keys
bit 1  WIN_TRK_OUTSIDE   ; возвращать клик вне всех объектов (WIN_EV_OUTSIDE)
bit 2  WIN_TRK_HALT      ; HALT в каждой итерации win_track (уступить процессор)
bit 3  WIN_TRK_SHOW_CUR  ; только win_track: показать курсор при входе в
                         ; блокирующий цикл, скрыть перед возвратом события;
                         ; для win_poll: курсор уже показан приложением,
                         ; библиотека может временно HIDE/SHOW при repaint
bit 4  WIN_TRK_TAB_FOCUS ; обрабатывать Tab/Shift+Tab как обход фокуса (§14.5)
```

### 14.2 Две функции

- `win_poll(DE=&WinTrack)` — **одна неблокирующая итерация**. Если события
  нет, возвращает `A=0`, `event=WIN_EV_NONE`. Предназначена для приложений
  с фоновой работой: чтение каталога, распаковка, сеть.
- `win_track(DE=&WinTrack)` — блокирующая обёртка: повторяет итерацию, пока
  событие не появится. При `WIN_TRK_HALT` между итерациями выполняет
  `HALT`, уступая процессор.

Обе функции полностью эквивалентны по обработке событий и состоянию;
`win_track` не делает ничего, чего нельзя сделать циклом вокруг
`win_poll` — за одним исключением: постоянной видимостью курсора
`win_poll` не управляет. Для `win_track` `WIN_TRK_SHOW_CUR` означает показ
при входе в блокирующий цикл и скрытие перед возвратом;
приложение, работающее через `win_poll`, показывает и прячет курсор само
(BIOS `C=1`/`C=2`), обычно один раз вокруг всего цикла, и устанавливает
`WIN_TRK_SHOW_CUR`, сообщая библиотеке, что cursor overlay нужно временно
убирать вокруг repaint. Сам `win_poll` постоянную видимость не меняет:
выполняет только парный HIDE/SHOW при собственной перерисовке. Если бит
сброшен, обе функции считают курсор скрытым и не вызывают HIDE/SHOW вокруг
рисования.

Первый `win_poll`/`win_track` только синхронизирует уже зажатые кнопки: он
не создаёт ложного фронта LMB/RMB. Порядок выбора строгий: действие
LMB/capture/repeat, затем RMB, затем отложенные LEAVE/HOVER, и лишь затем
клавиатура. Поэтому hover, совпавший с кликом, возвращается следующей пустой
итерацией; при выбранном mouse-событии SCANKEY не вызывается и клавиша не
теряется.

### 14.3 Таблица клавиш `WinKey` (4 байта на запись)

```text
offset size field
0      1    ascii       ; 0 = сравнивать только скан-код
1      1    scan        ; 0 = сравнивать только ASCII
2      1    mods        ; требуемые модификаторы (маска байта B DSS SCANKEY)
3      1    id
```

Длина задаётся полем `WinTrack.key_count`, терминатора нет. Сравнение —
как в gfxview: из скан-кода сбрасывается бит 7; события с модификаторами,
не совпавшими с `mods`, по таблице не матчатся (но при `WIN_TRK_ANY_KEY`
возвращаются как `WIN_EV_KEY`).

### 14.4 Итерация и hit-test

Итерация: чтение мыши (`RST #30, C=3`) → hit-test → обслуживание
hover/press/repeat → `DSS SCANKEY` → Tab-обход (если включён) → таблица
клавиш. Оптимизация gfxview сохраняется: если координаты, кнопки и
содержимое `state` не изменились, hit-test пропускается.

Прямоугольник объекта — **полуоткрытый**: точка `(mx,my)` попадает в
объект, если

```text
x <= mx - origin_x < x + width
y <= my - origin_y < y + height
```

Смежные объекты, у которых `x2 = x1 + width1`, не перекрываются и не имеют
щели. Перебор идёт **по убыванию индекса**, побеждает первый совпавший:
объект, нарисованный последним (то есть лежащий сверху), первым получает
событие. Тестируются только записи с `WIN_IT_HIT` без `WIN_IT_HIDDEN` и
`WIN_IT_DISABLED`; тип объекта на участие в hit-test не влияет (§12.3).

События (`event`):

| Код | Имя | Когда возвращается |
|---:|---|---|
| 0 | `WIN_EV_NONE` | только `win_poll`: событий нет |
| 1 | `WIN_EV_LCLICK` | обычный объект: LMB нажата и отпущена внутри; объект с `WIN_IT_REPEAT`: начальное нажатие |
| 2 | `WIN_EV_RCLICK` | RMB нажата над объектом |
| 3 | `WIN_EV_REPEAT` | очередной тик автоповтора (`WIN_IT_REPEAT`), LMB ещё удерживается |
| 4 | `WIN_EV_HOTKEY` | клавиша совпала с записью `WinKey` |
| 5 | `WIN_EV_KEY` | любая клавиша при `WIN_TRK_ANY_KEY`; сырые коды в `key_*` |
| 6 | `WIN_EV_HOVER` | курсор вошёл в объект с `WIN_IT_HOVER` |
| 7 | `WIN_EV_LEAVE` | курсор покинул объект с `WIN_IT_HOVER` (`id`/`index` — покинутого) |
| 8 | `WIN_EV_OUTSIDE` | LMB/RMB вне всех hit-объектов при `WIN_TRK_OUTSIDE` (`id=#FF`, `index=#FF`) |
| 9 | `WIN_EV_FOCUS` | фокус перемещён Tab/Shift+Tab (§14.5) |
| 10 | `WIN_EV_CHANGE` | библиотека фактически изменила checkbox/radio (§16.5) |

Помимо `D=event`, `E=id` приложение получает полный контекст в полях
`WinTrack`: индекс записи, подобласть, координаты, кнопки, сырые коды
клавиши, `user_data`. Обработав событие, приложение выставляет
`WIN_IT_DIRTY` изменившимся объектам, вызывает `win_update` и снова
входит в `win_poll`/`win_track`. Исключение — `WIN_EV_CHANGE`: состояние и
перерисовка checkbox/radio уже завершены библиотекой (§16.5).

`part` — подобласть внутри составного контрола:

| Контрол | `part` |
|---|---|
| `WIN_T_SCROLLBAR` | 1 стрелка «назад», 2 стрелка «вперёд», 3 страница назад, 4 страница вперёд, 5 ползунок |
| `WIN_T_LISTBOX` | 1 строка (индекс строки — в `item`) |
| остальные | 0 |

Подобласти вычисляются внутри hit-test по геометрии контрола; ползунок —
по `thumb_pos`/`thumb_len`, то есть по последней **нарисованной** геометрии:
визуальное и интерактивное положение ползунка совпадают по построению.
Никаких внешних записей зон скроллбар не создаёт и не изменяет.

Для listbox библиотека вычисляет
`item = first + (my - origin_y - y_content) / item_height` по связанному
`WinListbox`, где `y_content` учитывает отступ рамки (§16.4); строки за
пределами `total` дают `item=#FFFF` и `part=0`.

**Клик и автоповтор.** `WIN_IT_PRESS` управляет только визуальной
анимацией и не меняет момент события. Для обычного объекта `WIN_EV_LCLICK`
возвращается после press+release внутри той же зоны; отпускание снаружи
отменяет клик. Для объекта с `WIN_IT_REPEAT` первый `WIN_EV_LCLICK`
возвращается сразу при нажатии, далее идёт пауза `repeat_delay` итераций и
`WIN_EV_REPEAT` каждые `repeat_rate` итераций, пока LMB удерживается над
той же зоной; отдельного `LCLICK` при отпускании нет. Значения по умолчанию
12 и 3 задаются build-time константами
`WIN_REPEAT_DELAY`/`WIN_REPEAT_RATE`.

Библиотека считает собственные итерации опроса.
Итерация не является кадром: `HALT` пробуждается любым прерыванием, а
кроме кадрового INT на Sprinter существуют независимые источники CTC и
COVOX/CBL (§3.5), конфигурацию которых задаёт приложение. Поэтому темп
выражен в итерациях, а не в миллисекундах или кадрах, и приложение с
собственным источником прерываний или без `WIN_TRK_HALT` обязано
скорректировать `repeat_delay`/`repeat_rate` под свой темп цикла.

Выход из repeat-объекта сбрасывает задержку; возврат при всё ещё зажатом LMB
не создаёт второго `WIN_EV_LCLICK`. Для обычного capture временный выход и
возврат допустимы, но click приходит только после release внутри исходного
объекта.

`win_wait_release` — аналог `ResFire`: ждёт отпускания всех кнопок мыши
(и опустошает клавиатурный буфер), используется перед входом в новый
модальный цикл.

`win_set_cursor(E, IX)` — форма курсора: `E=0` стрелка, `E=1` «ожидание»,
`E=#FF` — пользовательский спрайт, тогда `IX=&WinCursor`:

```text
offset size field
0      1    width       ; 1..32
1      1    height      ; 1..32
2      1    hot_x
3      1    hot_y
4      ...  width*height байт в формате BIOS (§3.3)
```

Пользовательский курсор принимает стороны 1..32, hotspot строго внутри
изображения и не более 256 пикселей. После успешной локальной проверки entry
делает только BIOS LOAD CURSOR: он не меняет видимость и не выполняет `HALT`.

### 14.5 Фокус клавиатуры и Tab-обход

Реализуется на этапе 4; поле `WinWindow.focus`, флаг `WIN_IT_FOCUSABLE`,
опция `WIN_TRK_TAB_FOCUS` и флаги фокуса контролов занимают позиции,
зарезервированные с этапа 2, и не меняют размеры структур.

**Единственный источник истины в декларативном пути — `WinWindow.focus`**
(индекс записи `WinItem`, `#FF` = фокуса нет). Фокус хранится в
дескрипторе окна, а не в библиотеке и не в трекере: окно «помнит» свой
фокус между разными циклами опроса. Начальный фокус приложение задаёт
этим полем до первого `win_draw`, а `last_focus=#FF`. Для программной
смены приложение записывает новый `focus` и вызывает `win_update`;
библиотека сравнивает его с `last_focus` и сама обновляет оба индикатора.

При `WIN_TRK_TAB_FOCUS` Tab и Shift+Tab перемещают фокус к
следующей/предыдущей записи с флагом `WIN_IT_FOCUSABLE` (циклически;
записи с `WIN_IT_DISABLED` и `WIN_IT_HIDDEN` пропускаются) и возвращают
`WIN_EV_FOCUS`. Tab обрабатывается раньше таблицы `keys`.
Все доступные `WIN_T_RADIOBUTTON` с одинаковым `group` внутри одного
`WinWindow` образуют одну Tab-остановку: представителем служит checked-
элемент, а при его отсутствии — первый доступный элемент группы.

**Индикатор фокуса рисует библиотека.** При каждом перемещении фокуса она
до возврата события снимает индикатор со старой записи и рисует на новой
для встроенных контролов, перечисленных ниже. Способ определяется полем
`type`:

| `type` | Индикатор |
|---|---|
| `WIN_T_BUTTON` | флаг `WIN_BTN_FOCUS`, перерисовка кнопки: пунктирный прямоугольник внутри рамки с отступом 2 px |
| `WIN_T_LISTBOX` | флаг `WIN_LB_FOCUS`, перерисовка строки курсора: с фокусом — `WIN_TH_CURSOR_*`, без фокуса — `WIN_TH_FACE`/`WIN_TH_TEXT` |
| `WIN_T_EDIT` | флаг `WIN_ED_FOCUS`, перерисовка поля: с фокусом виден текстовый курсор |
| `WIN_T_CHECKBOX`, `WIN_T_RADIOBUTTON` | флаг `WIN_CH_FOCUS`, пунктир вокруг области подписи |
| `WIN_T_ZONE` и прочие | автоматического индикатора нет; приложение решает, нужен ли он |

В реализации этапа 4 строка `WIN_T_LISTBOX` фиксирует будущую семантику,
но сам тип и `WIN_LB_FOCUS` ещё возвращают `WIN_ERR_UNSUPPORTED`. Они
включаются вместе с `win_listbox_draw` и `WIN_CAP_LISTBOX` на этапе 5.

Флаги `WIN_BTN_FOCUS`/`WIN_LB_FOCUS`/`WIN_ED_FOCUS`/`WIN_CH_FOCUS` — **производное
представление**, необходимое, чтобы обычные функции отрисовки контролов
рисовали согласованное состояние. В декларативном пути их пишет только
библиотека: `win_draw`, `win_update` и каждое перемещение фокуса
выставляют флаг контролу под `focus`, снимают его с `last_focus`, затем
обновляют `last_focus`. `win_draw_item` синхронизирует только переданный
объект и не является операцией смены фокуса. Приложение производные флаги
не трогает, пока работает через `WinWindow`, поэтому у них один писатель.
Вручную флаги используются только в чисто императивном сценарии — прямые
вызовы контролов без окна.

Благодаря синхронизации флагов встроенный индикатор выглядит одинаково
при обходе Tab, при построении окна `win_draw` и при точечном обновлении
контрола приложением: прямой вызов рисует по уже синхронизированному
флагу.

Для `WIN_T_ZONE` и пользовательских контролов библиотека меняет
`WinWindow.focus` и возвращает `WIN_EV_FOCUS`, но ничего не рисует:
самообратимый XOR нельзя сделать идемпотентным для произвольного
`win_draw_item`. Если индикатор нужен, приложение перерисовывает свой
контрол и вызывает `win_focus_rect` явно на переходах focus.

Индикатор всегда рисуется внутри границ контрола и не задевает соседние
объекты.

Enter при фокусе на `WIN_T_BUTTON` возвращает `WIN_EV_LCLICK`
этого объекта — клавиатурная активация с анимацией нажатия. Space
активирует только checkbox/radio (§16.5); `buttons=0`,
`mouse_x/y` к событию не относятся. Клик мышью по объекту с
`WIN_IT_FOCUSABLE` также переводит на него фокус со сменой индикатора
(отдельное событие не генерируется — приложение получает сам клик).

Событие `WIN_EV_FOCUS` существует не ради отрисовки, а чтобы приложение
могло реагировать на смену фокуса содержательно: показать подсказку в
статусной строке, подгрузить данные, запустить `win_edit` для поля ввода.

Перед собственными перерисовками (анимация кнопки, смена индикатора
фокуса) `win_poll`/`win_track` выполняют парный HIDE/SHOW, если установлен
`WIN_TRK_SHOW_CUR` (§14.2). Hover библиотека только сообщает событием;
его визуальную реакцию рисует приложение.

## 15. Поле ввода

### 15.1 `WinEdit` (16 байт)

```text
offset size field
0      2    x
2      2    y
4      2    width
6      2    height      ; >= 8 без рамки, >= 12 с рамкой
8      1    attr        ; #FF = WIN_TH_FIELD_FG на WIN_TH_FIELD_BG
9      1    flags
10     1    maxlen      ; максимум символов, 1..63
11     1    len         ; internal-кэш: длина, вычисленная из буфера
12     1    cursor      ; позиция курсора (индекс символа)
13     1    scroll      ; первый видимый символ (гор. прокрутка длинных строк)
14     2    buffer      ; указатель на буфер maxlen+1 байт
```

`flags`:

```text
bit 0  WIN_ED_FRAME     ; рисовать sunken-рамку вокруг поля
bit 1  WIN_ED_FOCUS     ; поле в фокусе, текстовый курсор виден
bit 2  WIN_ED_PASSWORD  ; выводить '*' вместо символов
```

При `WIN_ED_FRAME` содержимое поля отступает на 2 px от каждой границы
(1 px sunken-рамки + 1 px зазора); та же content-область используется
hit-test'ом.

`win_edit_draw` — отрисовка поля без интерактива: рамка (по флагу), фон,
видимая часть строки; текстовая каретка — вертикальная линия на границе
символа — рисуется только при `WIN_ED_FOCUS`. В framed-поле сплошная линия
имеет размер `1×10` и выступает на пиксель выше и ниже 8-пиксельного глифа;
в минимальном поле без рамки она остаётся `1×8`. Каретка использует цвет
текста. Перед её выводом все закрываемые пиксели сохраняются, а перед
миганием или перерисовкой точно восстанавливаются. Поэтому каретка заметна
рядом с высокими штрихами `t`, `h`, `l`, остаётся непрерывной поверх
парольного `*`, не зависит от XOR-маски темы и не оставляет следов. У
статического `win_edit_draw` каретка остаётся видимой.

**Источник истины о содержимом — сам буфер.** Его формат определяется
`win_set_text_format` (§9.2): ASCIIZ либо байт длины + символы; последний
напрямую совместим со `string[maxlen]` Turbo Pascal. На входе каждого
вызова `win_edit_draw`/`win_edit` библиотека вычисляет длину из буфера
(по терминатору `#00` или байту длины), записывает её в кэш `len` и
нормализует `cursor`/`scroll` к этой длине; в ходе редактирования она
поддерживает буфер и `len` согласованными. Приложению достаточно
заполнить буфер — синхронизировать `len` вручную не нужно.

Проверка ограничена ёмкостью: в ASCIIZ-режиме `#00` обязан встретиться не
позже `buffer[maxlen]`, в Pascal-режиме первый байт обязан быть
`<=maxlen`. Иначе функция возвращает `WIN_ERR_ARGUMENT`, не изменяя
дескриптор и буфер.

### 15.2 `win_edit` — модальное редактирование

`DE=&WinEdit`, `IX=&WinTrack` (0 — работать без мыши). Библиотека
обрабатывает клавиши: печатные `>=#20` (вставка с учётом `maxlen` и
пропорциональной ширины поля), Backspace, Delete, Left/Right, Home/End.
Ctrl+Left/Right перемещают курсор по словам; как в FlexNavigator,
разделителями считаются пробел, запятая, точка и обратная косая черта.
Прокрутка `scroll` поддерживает строки шире поля. Исходное содержимое
запоминается для отката по Esc. На входе выставляется `WIN_ED_FOCUS`, на
выходе снимается. Во время редактирования рамка не перерисовывается:
символы сразу замещают старую строку своими фонами, затем очищается только
неиспользованный хвост content-области. Это исключает промежуточный пустой
кадр и мерцание bevel-рамки.

Каретка мигает с периодом 14 пустых итераций: после каждого `HALT` счётчик
уменьшается, а на нуле переключается только сплошная линия `1×10` (`1×8` без
рамки) с сохранением/восстановлением фона. Перед изменением текста или позиции
курсора видимая каретка сначала целиком восстанавливается, включая верхний и
нижний пиксели вне полосы глифа. Пустая итерация `win_edit` всегда выполняет
`HALT`, в том числе если переданный `WinTrack` не содержит `WIN_TRK_HALT`;
это даёт каретке стабильную кадровую базу.

При смене фокуса по Tab, мыши или программно через `WinWindow.focus` +
`win_update` декларативный путь перерисовывает у `WinEdit` только
content-область: рамка и общий фон контрола остаются на экране. Каретка сначала
восстанавливает сохранённые пиксели, поэтому переход между полем и кнопкой не
создаёт пустого кадра или вспышки bevel-рамки.

`WIN_EV_LCLICK` по тому же `WinEdit`, который сейчас редактируется, не
завершает `win_edit`: координата `mouse_x` преобразуется в индекс по реальным
пропорциональным ширинам видимых символов, курсор переносится к выбранному
глифу, поле перерисовывается и цикл редактирования продолжается. Клик по
другому объекту сохраняет прежнее поведение `WIN_ED_MOUSE`.

Возврат `E=reason`:

```text
0  WIN_ED_ENTER   ; Enter — буфер принят
1  WIN_ED_ESC     ; Esc — исходная строка восстановлена (и перерисована)
2  WIN_ED_TAB     ; Tab — буфер принят; при переданном WinTrack с
                  ; WIN_TRK_TAB_FOCUS библиотека сама перевела фокус на
                  ; следующий объект и перерисовала индикаторы (новый
                  ; индекс — в WinWindow.focus)
3  WIN_ED_MOUSE   ; событие мыши по другому объекту окна из WinTrack; само
                  ; событие заполнено в WinTrack, буфер принят
```

При `IX=0` события мыши не проверяются. Аналог FN `InputLine` +
`InpLnExtN`/`InpLnExtC`, но без передачи управления по адресам.

## 16. Контролы post-MVP

### 16.1 Иконка: `win_icon`

`WinIcon` (12 байт):

```text
offset size field
0      2    x
2      2    y
4      2    width       ; только 8 или 16
6      2    height      ; равно width
8      1    flags       ; bit 0 WIN_ICO_KEYED: байт #FF прозрачен
9      1    page        ; физическая EMM-страница с ячейками
10     1    slot        ; номер ячейки внутри страницы
11     1    reserved = 0
```

Геометрия остаётся в общем 8-байтном заголовке, поэтому универсальный
hit-test не разбирает формат изображения. ABI 1.0 принимает два
квадратных размера:

```text
8×8:    64 байта на ячейку, 256 слотов/страницу,
        source_offset = slot << 6, slot 0..255
16×16: 256 байт на ячейку,  64 слота/страницу,
        source_offset = slot << 8, slot 0..63
```

Страница однородна: она целиком содержит либо 8×8, либо 16×16 ячейки.
Пиксели каждой ячейки лежат row-major без заголовка и padding. Благодаря
этому адрес источника получается из `page`, `slot` и `width` за `O(1)`,
без таблицы указателей и деления. `page` — физический номер из массива,
возвращённого BIOS EMM после выделения блока; DLL временно подключает его
в data-окно и не владеет этой памятью. DLL валидирует размер и диапазон
slot, но без заголовка в EMM не может проверить тип страницы; соответствие
гарантируют `winiconpack` и приложение. Ошибка типа рисует не тот участок
той же страницы, но не выводит чтение за её границу.

Пиксели иконки — полные 8-битные индексы палитры (не 4-битные `color`):
иконки могут использовать любые из 256 цветов. Вывод построчно
акселераторным `COPY` непосредственно EMM→VRAM. Ячейка по построению не
пересекает границу 16 КБ, поэтому промежуточный CPU-буфер и место под
графику в WIN0..WIN2 не требуются.

Прозрачность выполняется **аппаратно**: при `WIN_ICO_KEYED` запись идёт
через VRAM-алиас `#58` (прозрачность байта `#FF` с обновлением DRAM-зеркала,
`gfx320/specs.md` §3.3), а не CPU-циклом с проверкой каждого байта. Зеркало
при этом остаётся корректным, поэтому область под keyed-иконкой можно
сохранять в backstore.

16×16 — основной размер UI-иконки; 8×8 предназначен для мелких маркеров,
стрелок и составных контролов. Более крупное изображение собирается из
нескольких 16×16 записей. В декларативном окне каждая `WIN_T_ICON` может
получать клики обычным `WIN_IT_HIT`. Нескольким ячейкам составного
контрола можно назначить один `id`, либо накрыть их последней невидимой
`WIN_T_ZONE`; никакого специального callback-ABI для иконок нет.
Императивный `win_icon` только рисует — события появляются при наличии
`WinItem` и вызове `win_poll`/`win_track`.

В поставку входит host-инструмент `winiconpack`. Он нарезает PNG/BMP или
sprite sheet на ячейки 8×8/16×16 и создаёт:

- файл `WIP1` с однозначным little-endian форматом:

```text
offset size field
0      4    magic = "WIP1"
4      1    version = 1
5      1    page_count          ; 1..255
6      2    header_size         ; 8 + page_count*2
8      2*N  pages[N]            ; {cell_size 8|16, used}
header_size
       16384*N payload[N]       ; offset = header_size + page_index*16384
```

  `used=0` означает 256 ячеек только для страницы 8×8; для 16×16
  допустимо `used=1..64`. Неиспользованный хвост каждого payload
  заполняется `#FF`;
- manifest для asm/C/Pascal с тройкой
  `{pack_page, slot, size}` для каждого имени ассета.

`WIP1` не содержит палитру: payload хранит уже готовые 8-битные индексы,
а палитрой экрана владеет приложение. Для keyed-ассетов индекс `#FF`
зарезервирован под прозрачность; packer принимает indexed PNG либо явную
таблицу преобразования цветов и не выполняет неявную квантизацию.

Загрузчик примера выделяет `page_count` EMM-страниц, загружает payload и
один раз заменяет `pack_page` в рабочих `WinIcon` на соответствующий
физический номер. Библиотека не хранит глобальную таблицу icon-pack:
прямой физический `page` экономит состояние и одно косвенное чтение в
горячем пути.

### 16.2 Прогрессбар: `win_progress_init` / `win_progress_draw`

`WinProgress` (12 байт, поле `internal` заполняет init — модель FN
`InitProcess`/`PrnProcess`):

```text
offset size field
0      2    x
2      2    y
4      2    width       ; px
6      2    height      ; px, >= 3
8      1    flags       ; bit 0 WIN_PG_FRAME: sunken-рамка вокруг
9      1    percent     ; 0..100, обновляется приложением
10     2    last_px     ; internal: последняя граница; #FFFF = полный рендер
```

Единица ABI всегда процент. Значения `101..255` дают `WIN_ERR_ARGUMENT`.
Приложение один раз переводит свой счётчик (байты файла, число объектов и
т. п.) в `0..100`; внутри контрола выполняется только неизбежное
преобразование процента в координату пикселя. Полей `max`, коэффициента и
двойного масштабирования нет. Однобайтный процент одинаково удобен для
ассемблера, SDCC и Turbo Pascal.

Цвета берутся из темы (`WIN_TH_PROGRESS`/`WIN_TH_PROGRESS_FILL`).

`win_progress_init` проверяет геометрию/процент и ставит
`last_px=#FFFF`. `win_progress_draw` вычисляет границу как
`floor(inner_width*percent/100)` с 16-битным промежуточным значением;
`percent=100` точно даёт `inner_width`. При sentinel контрол рисуется
полностью, иначе — только полоса между `last_px` и новой границей
(регресс перерисовывается фоном). Если новое значение попадает в тот же
пиксель, запись в VRAM не выполняется. Изменение `width`, `height` или
flags требует повторного `win_progress_init`.

### 16.3 Скроллбар: `win_scrollbar_init` / `win_scrollbar_draw`

`WinScrollbar` (22 байта):

```text
offset size field
0      2    x
2      2    y
4      2    width       ; вертикальный: толщина (>= 6, типово 8); горизонтальный: длина
6      2    height      ; вертикальный: длина; горизонтальный: толщина
8      2    visible     ; видимых элементов
10     2    total       ; всего элементов
12     2    first       ; первый видимый (обновляется приложением)
14     1    flags       ; bit 0 WIN_SB_HORIZONTAL, bit 1 WIN_SB_ARROWS
15     1    reserved = 0
16     2    thumb_pos   ; internal, px от начала трека
18     2    thumb_len   ; internal, px
20     2    last_pos    ; internal: последняя нарисованная позиция; #FFFF = полный рендер
```

Геометрия задана общим заголовком: длина и толщина трека выводятся из
`width`/`height` и ориентации, отдельных полей нет.

Разделение обязанностей: `win_scrollbar_init` только валидирует дескриптор
и ставит `last_pos=#FFFF` (sentinel полного рендера) — он вызывается один
раз. `win_scrollbar_draw` **сам** пересчитывает геометрию ползунка из
текущих `first/visible/total`
(`thumb_len = max(track*visible/total, WIN_SB_MIN_THUMB)`, позиция — из
`first/total`; `total<=visible` растягивает ползунок на весь трек), при
sentinel рисует полностью, иначе очищает только прежний прямоугольник
ползунка и сразу рисует новый, после чего обновляет
`thumb_pos`/`thumb_len`/`last_pos`. Изменение `first` требует только
`draw` (или `WIN_IT_DIRTY` + `win_update`) — повторный `init` при каждом
сдвиге уничтожал бы выгоду инкрементального рендера. Трек использует
`WIN_TH_SCROLL_TRACK`, а объёмный ползунок — `WIN_TH_FACE`, как обычная
кнопка; концевые кнопки используют те же роли бевеля и тела.

Допустимые значения: при `total=0` требуются `visible=0, first=0`; при
`total>0` требуется `visible>0`, а `first <= max(total-visible,0)`.
Некорректное состояние возвращает `WIN_ERR_ARGUMENT`, а не молча
исправляется — источник истины остаётся у приложения.

Перед пересчётом `draw` сохраняет прежние `thumb_pos` и `thumb_len` в
scratch. Если изменилась длина, он восстанавливает track под объединением
старого и нового прямоугольников и рисует новый thumb; изменение только
позиции обрабатывается тем же путём без полного рендера.

При `WIN_SB_ARROWS` скроллбар сам рисует на концах трека контрастные
квадратные кнопки прокрутки и сам обслуживает их в
hit-test. Внешних объектов и записей зон под стрелки и страницы не
требуется: подобласти возвращаются в `WinTrack.part` (§14.4). Это снимает
приём gfxview/FN с «живой» таблицей зон, координаты которой контрол
переписывал на каждой отрисовке.

Клики по стрелкам и страницам покрывают навигацию в 1.0.
Перетаскивание ползунка — возможное совместимое расширение после 1.0,
если его востребованность подтвердят приложения.

### 16.4 Listbox: `win_listbox_draw`

Для небольших динамических списков (например, уже находящегося в памяти
приложения результата чтения каталога) сохраняется самый дешёвый формат:
массив обычных 16-битных указателей на строки. Для большого списка,
который не стоит держать в WIN0..WIN2, используется `WinTextRef`
(3 байта):

```text
offset size field
0      1    page        ; физическая EMM-страница строки
1      2    offset      ; 0..16383, смещение строки в странице
```

Строка имеет текущий формат `WIN_TXT_ASCIIZ`/`WIN_TXT_PASCAL` и вместе с
терминатором либо байтом длины обязана целиком находиться в указанной
странице. Страницы могут иметь любые физические номера и не обязаны быть
смежными. При упаковке длинного набора хвост страницы просто остаётся
свободным, если следующая строка в него не помещается; ссылка следующей
строки уже содержит номер другого физического EMM-блока.

`WinListbox` (28 байт):

```text
offset size field
0      2    x
2      2    y
4      2    width         ; px
6      2    height        ; px, полная высота поля
8      1    item_height   ; px, >= 8
9      1    attr_normal   ; #FF = WIN_TH_FIELD_FG на WIN_TH_FIELD_BG
10     1    attr_cursor   ; #FF = WIN_TH_CURSOR_FG на WIN_TH_CURSOR_BG
11     1    flags
12     2    total         ; всего строк
14     2    first         ; первая видимая
16     2    cursor        ; абсолютный индекс строки курсора
18     2    items         ; direct: &u16[total]; paged: offset таблицы WinTextRef
20     1    items_page    ; paged: физическая EMM-страница таблицы
21     1    reserved = 0
22     2    scrollbar     ; &WinScrollbar или 0 (только синхронизация полей)
24     2    last_first    ; internal: последняя нарисованная позиция; #FFFF = полный рендер
26     2    last_cursor   ; internal: последняя нарисованная строка курсора
```

`flags`:

```text
bit 0  WIN_LB_FRAME     ; sunken-рамка вокруг поля
bit 1  WIN_LB_NOCURSOR  ; не выделять строку курсора
bit 2  WIN_LB_FOCUS     ; список в фокусе
bit 3  WIN_LB_PAGED     ; items — таблица WinTextRef в физической EMM-странице
```

При сброшенном `WIN_LB_PAGED` поле `items` указывает на привычный
`u16[total]`, каждый элемент которого — обычный указатель на строку в
логической памяти приложения; `items_page` обязан быть нулём. Это лучший
вариант для небольшого изменяемого списка и не требует копирования имён
каталога в специальный формат.

При установленном `WIN_LB_PAGED` `items_page:items` задаёт физическую
страницу и смещение массива `WinTextRef[total]`. Весь массив ссылок обязан
помещаться в одной 16-КБ странице:
`items + total*3 <= 16384`; при `items=0` это до 5461 строк. Сами строки
могут лежать в любом количестве произвольных EMM-страниц, потому что
каждая запись несёт свой `page`. Для типичного большого каталога
приложение выделяет одну страницу таблицы ссылок и столько страниц текста,
сколько требуется именам. Библиотека подключает таблицу только для чтения
одной ссылки, затем отдельно копирует выбранную строку в `text_scratch` и
восстанавливает mapping до отрисовки. Поиск записи остаётся `O(1)`:
`items + index*3`.

Callback/provider ABI сознательно не вводится: он заметно усложнил бы
вызовы из C и Pascal и сделал бы mapping кода приложения во время DLL
небезопасным. Если одному экрану действительно требуется больше 5461
paged-записей, приложение показывает отфильтрованное/постраничное
представление; совместимое расширение с вектором страниц можно добавить
после ABI 1.0.

Content-область: при `WIN_LB_FRAME` содержимое отступает на 2 px от каждой
границы (1 px sunken-рамки + 1 px зазора), без рамки совпадает с
геометрией. Число видимых строк = `content_height / item_height` —
отдельного поля `visible` нет, чтобы геометрия не хранилась дважды.
Hit-test строк (§14.4) использует ту же content-область и ту же формулу.

Граничные состояния однозначны:

- `total=0`: `first=0`, `cursor=#FFFF`, `items` может быть 0;
- `total>0`: ссылка `items` допустима в выбранном direct/paged-режиме,
  `first<total`, `cursor=#FFFF` или
  `cursor<total`;
- content-область обязана вмещать хотя бы одну строку, иначе
  `WIN_ERR_ARGUMENT`.

Прямой вызов `win_listbox_draw` дифференциален: если `first` равен
`last_first`, перерисовываются только строки `last_cursor` и `cursor`.
При изменении `first` на одну строку содержимое переносится перекрывающимся
пиксельным accelerator-copy; затем рисуются только появившаяся крайняя
строка, прежний и новый курсоры. Более крупный переход перерисовывает все
видимые строки. Sentinel `last_first=#FFFF`
(приложение записывает его при инициализации структуры) принудительно
даёт полный рендер; `win_draw`/`win_draw_item` рисуют полностью всегда и
записывают в `last_*` актуальные значения (§12.4).

Если приложение заменило текст произвольной видимой строки, но не меняло
`first/cursor`, оно либо ставит `last_first=#FFFF` перед
`WIN_IT_DIRTY`, либо вызывает полный `win_draw_item`: по одним значениям
курсора библиотека не может узнать, какая внешняя строка изменилась.

Каждая строка — заливка фоном соответствующего атрибута + текст (обрезка по
`width` как у `WIN_LABEL_CLIP`); хвост ниже `total` заливается фоном
`attr_normal`. Строка `cursor` при `WIN_LB_FOCUS` заливается
`attr_cursor`, без фокуса — `WIN_TH_FACE`/`WIN_TH_TEXT`: позиция курсора
остаётся видимой, но список явно не активен.

Высота контента может быть не кратна `item_height`: для вывода, hit-test и
быстрой прокрутки она округляется вниз до целого числа строк. Оставшийся
нижний хвост сохраняется фоном поля; частично видимая строка не рисуется.

Связь со скроллбаром — **только синхронизация полей**: если задан
`scrollbar`, `win_listbox_draw` обновляет его `visible/total/first`, но не
рисует. Скроллбар — отдельная запись `WIN_T_SCROLLBAR` в том же списке
объектов (рекомендуется сразу после записи listbox: тогда при `win_update`
поля синхронизируются раньше его отрисовки); события его подобластей
приходят обычным путём §14.4. Приложение помечает `WIN_IT_DIRTY` обе
записи. В императивном сценарии — `win_listbox_draw`, затем
`win_scrollbar_draw`.

Навигацию (стрелки, PgUp/PgDn, клик по строке) реализует приложение:
события приходят из `win_poll`/`win_track` (объект listbox возвращает
индекс строки в `item`, клавиши — через `WinKey`), приложение меняет
`first/cursor`, ставит `WIN_IT_DIRTY` и вызывает `win_update`.

### 16.5 Checkbox и radio button: `win_checkbox` / `win_radiobutton`

Оба entry используют общий 14-байтный `WinChoice`:

```text
offset size field
0      2    x
2      2    y
4      2    width
6      2    height
8      1    attr        ; #FF = WIN_TH_TEXT на WIN_TH_FACE
9      1    flags
10     1    group
11     1    reserved = 0
12     2    text        ; текущий ASCIIZ/Pascal формат
```

```text
bit 0  WIN_CH_CHECKED
bit 1  WIN_CH_FOCUS      ; производный в декларативном пути
bit 2  WIN_CH_DISABLED
bits 3..7 reserved = 0
```

Минимальная геометрия — `13×10`: индикатор занимает `10×10`, подпись
начинается через 3 px от его правой границы, 8-пиксельный текст и сам
индикатор центрируются по вертикали. Контрол заполняет весь объявленный
прямоугольник цветом `WIN_TH_FACE`. Checkbox рисует sunken 3D-рамку и
пиксельную галочку; radio button — псевдокруглую светотеневую рамку и
центральную точку. Фокусный пунктир ограничен областью подписи. Тема не
расширяется: используются `FACE/TEXT`, `FIELD_BG`, `LIGHT/SHADOW`,
`TEXT_DISABLED` и `FOCUS_MASK`.

Для checkbox `group` обязан быть нулём. Для radio это явный `u8 0..255`;
группа действует только внутри того `WinWindow`, в котором находится
запись. Ненулевой `reserved`, слишком малая геометрия, недопустимый
указатель или ненулевой checkbox-group дают `WIN_ERR_ARGUMENT`, неизвестные
биты `flags` — `WIN_ERR_UNSUPPORTED`. Ошибка не меняет фокус, состояние,
dirty-флаги или экран.

Эффективное disabled-состояние задаётся любым из `WIN_IT_DISABLED` и
`WIN_CH_DISABLED`. Такой контрол рисуется приглушённо, но не участвует в
hit-test, Tab и клавиатурной активации. `WIN_IT_HIDDEN` также исключает его
из ввода и обхода.

Клик по любой части доступного контрола переводит фокус и выполняет действие:

- checkbox инвертирует `WIN_CH_CHECKED`;
- radio устанавливает `WIN_CH_CHECKED` у цели и снимает его у всех radio
  той же группы в окне, включая hidden/disabled записи;
- повторная активация уже выбранного radio поглощается без события.

Space выполняет то же действие для сфокусированного choice. Enter остаётся
клавишей кнопки. Для radio Left/Up (scan `#54/#58`) выбирают предыдущий,
Right/Down (`#56/#52`) — следующий доступный элемент группы, циклически и с
пропуском hidden/disabled. Встроенные `WinKey`, `WIN_EV_HOTKEY` и подписи с
`&` не получают специальной семантики.

После фактической смены библиотека возвращает `WIN_EV_CHANGE`; поля
`WinTrack.index/id/user_data` относятся к изменённому контролу. Фокус,
состояние и необходимые dirty-флаги публикуются до события, а библиотека
сама вызывает точечный `win_update`: у checkbox перерисовывается одна запись,
у radio — прежний и новый выбор. При `WIN_TRK_SHOW_CUR` вся операция имеет
одну пару HIDE/SHOW BIOS-курсора.

Для программного изменения отдельного setter-entry нет: приложение пишет
`WIN_CH_CHECKED`, устанавливает `WIN_IT_DIRTY` соответствующей записи и
вызывает `win_update`. Радиоэксклюзивность при этом является ответственностью
приложения; автоматическое снятие прежнего выбора выполняется только путями
мыши/клавиатуры библиотеки.

Два принципиальных отличия от FN:

1. обработчики не вызываются по адресам из таблиц — библиотека возвращает
   событие, приложение диспетчеризует само (окно приложения в момент
   исполнения DLL может быть размаплено). Флаги FN `d04..d09` (переход без
   возврата, автозакрытие окна) покрываются комбинацией `WIN_EV_*` +
   `win_close` на стороне приложения;
2. описание объекта и зона мыши — одна запись, а не две таблицы: FN
   требовал синхронно поддерживать координаты в описателе окна и в таблице
   `TestCoords`.

## 18. Внутреннее состояние и безопасность

### 18.1 Состояние DLL

```text
code_window, data_window_cfg, vram_window_cfg
screen (0/1), screen_offset (#000/#140)
origin_x, origin_y
theme[16], text_format
saved_work_pages[2], saved_iff
font_block (#FF = не выделен), font_page, font_valid

backstore_pages[4], backstore_count
alloc_top: {page_index, offset}          ; вершина bump-аллокатора (§13.3)
wnd_stack[4]: {x, y, w, h, screen, alloc_page, alloc_offset,
               prev_origin_x, prev_origin_y}, wnd_depth

text core state (из common/textcore320.inc):
             y_pos, print_color, bg_color, color_valid, колоночные буферы

descriptor_scratch (~32 байта)
text_scratch[256]                         ; также маска FN_ACC для invert
edit_undo[64]
```

Состояния трекинга здесь нет — оно живёт в `WinTrack.state` приложения
(§5.4). Буфер строки backstore тоже не нужен: обмен идёт напрямую между
двумя одновременно подключёнными окнами (§13.3).

Runtime-образ после инициализации занимает ровно одно 16-КБ окно. Код
checkbox/radio и остальных post-MVP контролов находится в relocatable overlay,
который `win_init` устанавливает поверх уже использованной libman bitmap
релокаций; дополнительная EMM-страница не выделяется. В хвосте файла после
WF32 хранятся четыре предварительно релокированных образа для WIN0..WIN3,
а загружается только нужный. `win320_layout.inc` является единым источником
`S5_OVERLAY_OFFSET/S5_OVERLAY_CODE_SIZE`; assembler assert и host-тест требуют
`offset+size=#4000`, поэтому ни один образ не пересекает `#10000`.

### 18.2 Аппаратная безопасность

Контракт акселератора идентичен `gfx320/specs.md` §15, но рабочие окна
динамические. Для каждой микропроцедуры библиотека:

1. проверяет параметры и копирует всё необходимое из памяти приложения в
   регистры/внутренний scratch;
2. определяет окно текущего `SP` и выбирает требуемые одно или два рабочих
   окна согласно `data_window_cfg`/`vram_window_cfg`, исключая окно DLL,
   окно `SP` и ещё нужные прямые операнды;
3. сохраняет состояние прерываний, выполняет `DI`, читает и сохраняет
   прежние номера страниц рабочих окон;
4. подключает `#50`/`#58` и, если требуется, физическую страницу font,
   backstore, иконок или paged-строк;
5. выполняет ограниченную группу операций акселератора; каждая блочная
   процедура завершается непосредственным `LD B,B`;
6. устанавливает `PORT_Y=#C0`, восстанавливает обе страницы;
7. выполняет `EI` только если прерывания были разрешены на входе, а затем
   при необходимости записывает изменённые поля обратно приложению.

Пока скрыто любое окно приложения, ISR не запускается: его код, стек или
данные могут находиться именно там. Внутри mapping запрещены `RST`,
BIOS/DSS-вызовы и обращения к скрытым данным приложения. Если выбран
WIN0, дополнительно требуется отсутствие активного источника NMI, потому
что `DI` не защищает вектор `#0066`. Окно текущего `SP` не переключается
никогда.

Для примитива достаточно одного VRAM-окна. Текст, backstore и иконка
требуют двух окон одновременно; иконка всегда использует прямой
EMM→VRAM путь (§16.1). Paged-строка сначала целиком копируется в
`text_scratch`, её mapping снимается, и только после этого подключаются
font+VRAM. Если подходящий набор окон найти невозможно, функция возвращает
`WIN_ERR_WINDOW` до изменения экрана. WIN0 не имеет особого ABI-статуса и
может быть data- либо VRAM-окном. При DLL→WIN3 и стеке в WIN0..WIN2 два
рабочих окна всегда существуют.

Атомарная единица — один глиф (до 8 колонок), одна строка иконки или одна
полная строка backstore (до 320 байт, `256 + остаток`, §13.3); между ними
прерывания разрешаются только с полностью восстановленными страницами.

Длинные операции (`win_draw` окна, `win_open`, listbox) делятся на
DI-секции не длиннее одной строки/одного объекта/одного глифа; `HALT`,
BIOS- и DSS-вызовы `win_poll`/`win_track` выполняются строго вне DI-секций
с восстановленными окнами. Бюджет DI-секции — build-time
`WIN_DI_BUDGET_US`, по умолчанию 200 мкс, проверяется на железе.

`win_init` (entry 0, вызывается из `l_load`): определяет окно кода по
старшему байту адреса (`AND #C0` + 2×`RLCA`), устанавливает обе настройки
рабочих окон в `WIN_WORK_AUTO`, сбрасывает состояние, загружает тему по
умолчанию, устанавливает начало отсчёта `0,0` и `PORT_Y=#C0`. Затем через
переданный в `A` file handle выделяет `font_block`, читает `WF32` из
  текущей позиции и сохраняет физический `font_page`, затем читает выбранный
  предварительно релокированный overlay в освобождённый хвост окна DLL. Один
  общий read/validate-путь используется также `win_load_font`. При ошибке
  полностью откатывает выделение и возвращает `CF=1`. Видеорежим, экран и
  палитру не трогает.

`win_set_work_windows` проверяет диапазон, различие явно заданных окон и
конфликт с окном DLL. Конфликт с `SP` дополнительно проверяется каждым
рисующим entry, поскольку приложение может переместить стек после
настройки.

`win_free` сначала закрывает оставшиеся модальные окна LIFO, восстанавливая
их фон, затем освобождает принадлежащий библиотеке `font_block`,
устанавливает `PORT_Y=#C0` и сбрасывает состояние. Это страховка для пути
`l_free`, который не использует код возврата fini; нормальный клиент всё
равно закрывает окна явно. Переданные backstore-страницы остаются
собственностью приложения и освобождаются им после выгрузки DLL. Для
cleanup библиотека временно выбирает рабочие окна автоматически, поэтому
фон восстанавливается и после назначения fixed-окна, совпавшего с
актуальным окном `SP`.
При частично завершившемся `win_init` значение `font_block=#FF`, поэтому
последующий cleanup из libman не освобождает страницу повторно.

## 20. Тестирование

Host-проверки (по образцу gfx320):

- размеры и смещения всех структур в `win320.inc` против эталона, включая
  совпадение 8-байтного заголовка геометрии у всех дескрипторов;
- при DLL в WIN3 одинаковые вызовы принимают дескриптор, строки, массивы
  и изменяемые буферы из каждого из WIN0, WIN1 и WIN2; для каждого
  возможного окна `SP` автоматика выбирает только остальные окна и
  byte-exact восстанавливает исходный mapping;
- явные настройки `win_set_work_windows`, AUTO+fixed и AUTO+AUTO дают
  одинаковый растр; конфликт fixed-окна с актуальным `SP` возвращает
  `WIN_ERR_WINDOW` до записи; иконки 8×8 и 16×16 вычисляют адреса слотов
  byte-exact, DLL отклоняет недопустимый slot, а `winiconpack` не создаёт
  страницу со смешанными размерами;
- отказ safe-проверок на граничных координатах с ненулевым началом
  отсчёта; `y+height=256` допустим, `257` — нет; 16-битное переполнение
  суммы отклоняется;
- неизвестные flag bits дают `WIN_ERR_UNSUPPORTED`, ненулевые
  `reserved` — `WIN_ERR_ARGUMENT`;
- полуоткрытость зон: смежные объекты не дают ни щели, ни перекрытия;
  порядок перебора по убыванию индекса; тестируются только записи с
  `WIN_IT_HIT`; `id=#FF` разрешён декоративной записи и отклоняется у
  интерактивной; `PRESS/REPEAT/HOVER` без `HIT` отклоняются;
- вычисление `item` и `part` для listbox и скроллбара, в том числе для
  пустого допустимого состояния и ошибочных сочетаний `total/visible`, а
  также для framed listbox (hit-test и отрисовка используют одну
  content-область); direct/paged listbox дают одинаковый растр,
  `items+total*3` не может выйти за физическую страницу, строка не может
  пересечь её границу, mapping восстанавливается после каждой строки;
- модель `WIN_IT_DIRTY`: `win_update` перерисовывает помеченные записи по
  возрастанию индекса и снимает флаг только после успешного draw;
  `win_draw` при успехе снимает флаг у всех; при ошибке агрегат
  останавливается, не снимая флаг ошибочной и последующих записей;
  dirty + focus-transition одного индекса дают одну перерисовку;
- изменение геометрии, порядка, hidden-состояния или темы между полными
  render требует `win_draw`; для перекрывающихся dirty-объектов
  восстановление z-order проверяется пометкой верхних записей;
- полный против дифференциального рендера: `win_draw`/`win_draw_item`
  игнорируют `last_*` и восстанавливают их; движение курсора listbox через
  `win_update` трогает ровно две строки; сдвиг `first` скроллбара не
  требует повторного `init`;
- bump-аллокатор backstore: строка никогда не пересекает границу страницы,
  ёмкость учитывает padding, `win_close` откатывает вершину; строка
  использует один mapping и одну либо две команды `COPY`;
- обход фокуса для вырожденных списков (нет фокусируемых записей, одна
  запись, все disabled); `last_focus` обеспечивает обновление прежнего и
  нового встроенного индикатора одним `win_update`; производные флаги
  соответствуют `WinWindow.focus` после полного draw/update;
- `WinChoice`: прямой/декларативный рендер и оба формата строк; click/Space,
  focus/disabled, независимые радиогруппы и снятие прежнего выбора; стрелки
  с wrap и пропуском hidden/disabled; ровно одна Tab-остановка на группу;
  программный `CHECKED+DIRTY`, повторный radio без `CHANGE`, точные
  `index/id/user_data`, баланс HIDE/SHOW и отсутствие мутации при ошибке;
- четыре предварительно релокированных overlay-образа имеют одинаковый
  размер; каждый укладывается до `#10000`, а все ссылки prefix на overlay
  отмечены в relocation bitmap;
- синхронизация `len` поля ввода с буфером в обоих форматах строк,
  ограниченный поиск терминатора и отказ без изменения буфера;
- самообратимость `win_focus_rect` (двойной вызов возвращает исходные
  байты) и соответствие типа объекта способу отрисовки фокуса;
- аппаратный `win_invert_rect` byte-exact совпадает с CPU-эталоном для
  ширин 1, 255, 256, 257 и 320, произвольных XOR-масок и обоих экранов;
  двойной вызов восстанавливает исходный растр и DRAM-зеркало;
- оба формата строк на одинаковом наборе данных дают одинаковый растр;
- byte-exact round-trip упаковки шрифтового блока; `WF32` начинается сразу
  после загружаемого prefix; INIT получает правильный handle и текущую
  позицию; отказ `l_load` на битом magic/версии/размере и утечек памяти
  нет; неудачный `win_load_font` оставляет прежний шрифт byte-exact.

Визуальный тест `WIN320.EXE` (MVP-профиль): включает режим `#81`,
`win_style`, рисует рабочий стол, открывает модальный диалог с кнопками и
лейблами, гоняет `win_track` (мышь + клавиши), обновляет отдельные объекты
через `WIN_IT_DIRTY` + `win_update`, закрывает окно с восстановлением
фона, повторяет на экране 1, восстанавливает видеорежим. Post-MVP профиль
добавляет edit/listbox/scrollbar/progress/icons и смену темы на лету. Отдельный
экран ABI 1.1 показывает обычный и disabled checkbox, две радиогруппы и
текущие значения; проверяются мышь, Tab/Shift+Tab, Space и radio-стрелки без
мерцания.

На реальном Sprinter обязательно проверить: восстановление фона под окном
поверх картинки (зеркало), keyed-иконку через `#58` с последующим
сохранением области в backstore, аппаратный XOR `win_invert_rect` с
масками `#00/#0F/#55/#FF`, поведение BIOS-курсора при перерисовках,
автоповтор и анимацию кнопок при активном COVOX/CTC-источнике прерываний,
оба экрана, отсутствие артефактов `PORT_Y`, длительность DI-секций,
восстановление исходных страниц всех выбранных рабочих окон после каждого
глифа/строки и каждой строки backstore, работу кадрового/звукового ISR во
время вывода длинного текста.

## 21. Поставка и биндинги

Библиотека рассчитана на три клиентских языка, представленных в экосистеме
Sprinter. ABI 1.1 стабилизируется сначала в нормативном asm-include;
обновление C/Pascal bindings отложено до следующего этапа стабилизации:

```text
win320/WIN320.DLL         ; готовая release-сборка, хранится в репозитории
win320/WIN320.EXE         ; визуальный тест для железа/эмулятора
win320/ICONS.WIP          ; release-ресурс визуального Stage-5 теста
win320/specs.md           ; это нормативное описание ABI
win320/win320.inc          ; sjasmplus: entry, коды ошибок, смещения и размеры
win320/bind/win320.h       ; последующий этап: SDCC struct + обёртки l_call
win320/bind/WIN320.INC     ; последующий этап: Turbo Pascal record + LibCall
win320/examples/dialog.asm ; один и тот же диалог на трёх языках
win320/examples/dialog.c
win320/examples/DIALOG.PAS
win320/tools/winiconpack.py ; PNG/BMP/sprite sheet → WIP1 + manifests
win320/examples/icons.wip  ; пример страничного набора 8×8/16×16
```

Штатный шрифт не поставляется отдельным файлом: `font.wf32` является
промежуточным артефактом сборки и первым trailing payload `WIN320.DLL`.
Отдельные WF32-файлы создаются пользователем только для `win_load_font`.

Требования к биндингам:

- смещения и размеры структур во всех трёх описаниях сверяются с
  ассемблерным эталоном автоматически, отдельной host-проверкой в
  `make verify`; расхождение — ошибка сборки;
- все структуры packed и не содержат полей, требующих выравнивания:
  только `u8` и `u16` little-endian, 32-битных величин в ABI нет вовсе,
  поэтому отсутствие `LongInt` в Turbo Pascal ничего не ограничивает;
- строки — по `win_set_text_format`: SDCC использует `WIN_TXT_ASCIIZ`, TPC —
  `WIN_TXT_PASCAL`, ассемблер любой; `WinTextRef` во всех биндингах packed
  и имеет ровно 3 байта;
- обёртки вызовов повторяют ограничения `l_call` (§5.3): только `A`, `DE`,
  `IX`, `IY`; для Pascal используется `LibCall` из `LIBMAN.INC`, как в
  `tpascal/dss_pascal_src/examples_pas/LIBDEMO.PAS`;
- каждый пример загружает DLL в WIN3. Код, стек и все данные интерфейса
  свободно размещаются в WIN0..WIN2; временные data/VRAM-окна библиотека
  выбирает сама. Явный `win_set_work_windows` нужен только приложению с
  особой раскладкой; изменяемые структуры (§5.5) остаются в writable RAM;
- примеры собирают один и тот же диалог (панель, два лейбла, поле ввода,
  две кнопки, listbox со скроллбаром), демонстрируя декларативный путь,
  прямой вызов, `WIN_IT_DIRTY` и цикл `win_poll`.
